## 14.1 `go test` 与测试文件
Go 的测试不需要额外框架。约定：

- 测试文件以 `_test.go` 结尾；
- 测试函数形如 `func TestXxx(t *testing.T)`；
- 测试文件和被测代码放在同一目录；
- 运行 `go test` 时，测试文件不会编进正常二进制。

先看一个最小例子。

`calc.go`：
```go
package calc

import "errors"

var ErrDivideByZero = errors.New("divide by zero")

func Add(a, b int) int { return a + b }

func Divide(a, b int) (int, error) {
    if b == 0 { return 0, ErrDivideByZero }
    return a / b, nil
}
```
`calc_test.go`：
```go
package calc

import "testing"

func TestAdd(t *testing.T) {
    got := Add(2, 3)
    if got != 5 {
        t.Errorf("Add(2, 3) = %d; want 5", got)
    }
}
```
运行：
```powershell
go test
```
输出：
```
ok  	example.com/calc	0.002s
```
加 `-v` 看每个测试：
```powershell
go test -v
```
输出：
```
=== RUN   TestAdd
--- PASS: TestAdd (0.00s)
PASS
ok  	example.com/calc	0.002s
```
常用命令：

| 命令 | 作用 |
|------|------|
| `go test` | 测试当前包 |
| `go test ./...` | 测试当前模块所有包 |
| `go test -v` | 显示每个测试 |
| `go test -run TestAdd` | 只运行匹配的测试（正则） |
| `go test -count=1` | 禁用结果缓存，强制重跑 |
| `go test ./pkg/...` | 测试指定子树 |

### 14.1.1 同包测试与外部测试包
`calc_test.go` 写 `package calc`，可以直接访问未导出标识符；也可以写 `package calc_test`，只通过公开 API 测试。

- 同包测试：适合测试内部实现、未导出函数；
- 外部测试包：适合验证公开契约，能发现「测试依赖内部细节」的问题。

不要为了测试把原本未导出的东西全部导出。

### 14.1.2 `t.Errorf` 与 `t.Fatalf`
| 方法 | 失败后的行为 | 使用场景 |
|------|--------------|----------|
| `t.Errorf` | 标记失败，继续执行 | 想收集多个错误 |
| `t.Fatalf` | 标记失败，立即 `Goexit` | 后续代码依赖前面的结果 |
| `t.Logf` | 只记录，不失败 | 调试信息、`-v` 时显示 |
```go
data, err := os.ReadFile(path)
if err != nil {
    t.Fatalf("read file: %v", err) // 读失败，后续断言没有意义
}
if string(data) != "hello" {
    t.Errorf("got %q; want %q", data, "hello")
}
```
`t.Fatalf` 必须在测试自己的 goroutine 里调用。在子 goroutine 里用 `t.Fatalf` 只会退出那个 goroutine，测试可能继续跑或挂起。

## 14.2 表驱动测试
同一个函数往往要测很多组输入。Go 的惯用写法是把用例放进切片：
```go
func TestAddTable(t *testing.T) {
    tests := []struct {
        name string
        a, b int
        want int
    }{
        {"正数", 2, 3, 5},
        {"负数", -2, -3, -5},
        {"零", 0, 0, 0},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            if got := Add(tt.a, tt.b); got != tt.want {
                t.Errorf("Add(%d, %d) = %d; want %d",
                    tt.a, tt.b, got, tt.want)
            }
        })
    }
}
```
运行 `go test -v`：
```
=== RUN   TestAddTable
=== RUN   TestAddTable/正数
=== RUN   TestAddTable/负数
=== RUN   TestAddTable/零
--- PASS: TestAddTable (0.00s)
    --- PASS: TestAddTable/正数 (0.00s)
    --- PASS: TestAddTable/负数 (0.00s)
    --- PASS: TestAddTable/零 (0.00s)
PASS
```
表驱动的价值：

- 加用例只加一行数据，不改测试逻辑；
- 失败信息带用例名，定位快；
- 方便统一检查边界、空值、错误路径。

错误信息要写清「输入、实际、期望」：
```go
t.Errorf("Add(%d, %d) = %d; want %d", tt.a, tt.b, got, tt.want)
```
不要只写 `t.Error("failed")`，否则 CI 里根本不知道哪组数据错了。

### 14.2.1 测试错误返回值
```go
func TestDivide(t *testing.T) {
    tests := []struct {
        name    string
        a, b    int
        want    int
        wantErr error
    }{
        {"正常", 10, 2, 5, nil},
        {"除零", 1, 0, 0, ErrDivideByZero},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got, err := Divide(tt.a, tt.b)
            if !errors.Is(err, tt.wantErr) { t.Fatalf("error = %v; want %v", err, tt.wantErr) }
            if got != tt.want {
                t.Errorf("Divide(%d, %d) = %d; want %d", tt.a, tt.b, got, tt.want)
            }
        })
    }
}
```
判断错误用 `errors.Is`，不要用 `err == wantErr`；后者遇到包装错误会失效（第 08 章）。

## 14.3 子测试 `t.Run`
`t.Run(name, func(t *testing.T){...})` 创建一个子测试：

- 名字会出现在 `-v` 输出和失败信息里；
- 可以单独运行：`go test -run 'TestAddTable/负数'`；
- 子测试名里的空格会被转换成下划线；
- 子测试可以嵌套。
```go
func TestUser(t *testing.T) {
    t.Run("Validate", func(t *testing.T) {
        t.Run("empty name", func(t *testing.T) { /* ... */ })
        t.Run("valid name", func(t *testing.T) { /* ... */ })
    })
}
```
运行单个子测试：
```powershell
go test -run 'TestAddTable/负数' -v
```
### 14.3.1 `t.Parallel`
```go
for _, tt := range tests {
    t.Run(tt.name, func(t *testing.T) {
        t.Parallel()
        // 这个子测试会与其他 Parallel 子测试并发执行
    })
}
```
规则：

- `t.Parallel` 会先暂停当前测试，等所有非并行测试跑完再并发执行；
- 并行测试不能共享可变全局状态；
- 并行测试里不能调用 `t.Setenv`；
- Go 1.22 起循环变量每次迭代新建，`tt` 不会互相覆盖；旧版本需要 `tt := tt`。

并行能缩短测试时间，但会把「测试之间互相污染」的问题暴露出来。先保证隔离，再开并行。

## 14.4 测试辅助：`t.Helper`、`t.Cleanup`、`t.TempDir`
### 14.4.1 `t.Helper`
```go
func assertEqual(t *testing.T, got, want int) {
    t.Helper()
    if got != want {
        t.Errorf("got %d; want %d", got, want)
    }
}

func TestAddHelper(t *testing.T) {
    assertEqual(t, Add(2, 3), 5)
}
```
没有 `t.Helper()` 时，失败会指向 `assertEqual` 内部；加上之后，失败行号指向调用方 `TestAddHelper`，更容易定位。

### 14.4.2 `t.Cleanup`
```go
func TestCleanupOrder(t *testing.T) {
    t.Cleanup(func() { t.Log("cleanup 1") })
    t.Cleanup(func() { t.Log("cleanup 2") })
    t.Log("test body")
}
```
`go test -v` 输出（行号随文件而变）：
```
=== RUN   TestCleanupOrder
    calc_test.go:45: test body
    calc_test.go:44: cleanup 2
    calc_test.go:43: cleanup 1
--- PASS: TestCleanupOrder (0.00s)
```
`Cleanup` 是后进先出（LIFO），适合关闭文件、回滚事务、恢复全局变量。它比 `defer` 更好的一点：即使测试在 helper 里提前返回，清理函数仍会执行。

### 14.4.3 `t.TempDir`
```go
func TestWriteFile(t *testing.T) {
    dir := t.TempDir()
    path := filepath.Join(dir, "a.txt")

    if err := os.WriteFile(path, []byte("hello"), 0644); err != nil { t.Fatal(err) }
    data, err := os.ReadFile(path)
    if err != nil { t.Fatal(err) }
    if string(data) != "hello" { t.Errorf("got %q; want %q", data, "hello") }
}
```
`t.TempDir()` 每次返回唯一目录，测试结束后自动删除，不需要手动 `RemoveAll`。

### 14.4.4 `t.Setenv`
`t.Setenv("APP_ENV", "test")` 设置环境变量并在测试结束自动恢复原值，但**不能在 `t.Parallel` 的测试中使用**，因为环境变量是进程级共享状态。

## 14.5 覆盖率
```powershell
go test -cover
```
假设目前只写了 `TestAdd`，输出类似：
```
ok  	example.com/calc	0.015s	coverage: 25.0% of statements
```
生成明细文件：
```powershell
go test -coverprofile=coverage.out ./...
go tool cover -func=coverage.out
```
输出：
```
example.com/calc/calc.go:7:	Add		100.0%
example.com/calc/calc.go:9:	Divide		0.0%
total:				(statements)	25.0%
```
生成 HTML：
```powershell
go tool cover -html=coverage.out -o coverage.html
```
浏览器打开 `coverage.html` 可以看到哪些行执行过。

要点：

- 覆盖率统计的是**语句是否执行**，不代表断言正确；
- 100% 覆盖率仍可能有 bug；
- 不要为了数字写没有意义的测试；
- 跨包统计用 `-coverpkg=./...`；
- 覆盖率报告文件不应提交到仓库（加入 `.gitignore`）。

## 14.6 基准测试
基准测试函数形如 `func BenchmarkXxx(b *testing.B)`：
```go
var sink string

func BenchmarkConcat(b *testing.B) {
    parts := []string{"Go", "Gin", "GORM"}

    b.ReportAllocs()
    b.ResetTimer()

    for i := 0; i < b.N; i++ {
        s := ""
        for _, p := range parts {
            s += p
        }
        sink = s // 防止编译器把计算优化掉
    }
}
```
运行：
```powershell
go test -bench=BenchmarkConcat -benchmem -run=^$ -count=1
```
输出类似（数字随机器变化）：
```
goos: windows
goarch: amd64
pkg: example.com/calc
cpu: Intel(R) Core(TM) i7-14650HX
BenchmarkConcat-24    	23805602	        48.61 ns/op	      16 B/op	       2 allocs/op
PASS
ok  	example.com/calc	2.645s
```
读懂输出：

| 列 | 含义 |
|----|------|
| `23805602` | 循环执行了约 2380 万次（`b.N` 自动调整） |
| `48.61 ns/op` | 每次操作约 48.61 纳秒 |
| `16 B/op` | 每次操作分配约 16 字节 |
| `2 allocs/op` | 每次操作分配 2 次 |

常用参数：
```powershell
go test -bench=.                 # 跑所有基准
go test -bench=. -benchmem       # 显示内存分配
go test -bench=. -benchtime=3s   # 每个基准至少跑 3 秒
go test -bench=. -count=5        # 重复 5 次，观察波动
```
基准测试注意事项：

- 准备数据放在循环外，必要时 `b.ResetTimer()`；
- 循环里必须使用 `b.N`，否则框架无法测量；
- 结果要写到包级变量或 `sink`，否则可能被优化掉；
- 不要在循环里做与测量目标无关的 I/O；
- 对比两个实现时，用同一台机器、同样的数据和参数。

`b.StopTimer()` / `b.StartTimer()` 可以排除初始化或清理耗时：
```go
b.StopTimer()
data := buildLargeData()
b.StartTimer()

for i := 0; i < b.N; i++ {
    use(data)
}
```

## 14.7 示例测试 `ExampleXxx`
示例测试既是文档，也是测试：
```go
func ExampleAdd() {
    fmt.Println(Add(2, 3))
    // Output: 5
}
```
`go test` 会运行它，并把实际输出与 `// Output:` 后面的内容逐字比较。输出不一致就失败。

命名规则：`Example` 对应包，`ExampleAdd` 对应函数 `Add`，`ExampleUser` 对应类型，`ExampleUser_Say` 对应方法；加后缀（如 `ExampleAdd_second`）可写额外示例。输出顺序不固定时把 `// Output:` 换成 `// Unordered output:`。示例测试适合放在包文档里，给使用者可直接运行的用法。

## 14.8 `httptest`：测试 HTTP
### 14.8.1 `NewRecorder`：不启动网络
```go
func helloHandler(w http.ResponseWriter, r *http.Request) {
    w.Header().Set("Content-Type", "application/json")
    json.NewEncoder(w).Encode(map[string]string{"message": "hello"})
}

func TestHelloHandler(t *testing.T) {
    req := httptest.NewRequest(http.MethodGet, "/hello", nil)
    rec := httptest.NewRecorder()

    helloHandler(rec, req)

    res := rec.Result()
    defer res.Body.Close()

    if res.StatusCode != http.StatusOK { t.Fatalf("status = %d; want %d", res.StatusCode, http.StatusOK) }

    var got map[string]string
    if err := json.NewDecoder(res.Body).Decode(&got); err != nil { t.Fatal(err) }
    if got["message"] != "hello" { t.Errorf("message = %q; want %q", got["message"], "hello") }
}
```
`httptest.NewRecorder()` 实现了 `http.ResponseWriter`，请求不会经过真实网络，速度快、结果稳定。

常用字段：
```go
rec.Code            // 状态码
rec.Body.String()   // 响应体
rec.Header()        // 响应头
rec.Result()        // *http.Response
```
### 14.8.2 `NewServer`：启动真实测试服务器
```go
func TestPingServer(t *testing.T) {
    srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        fmt.Fprint(w, "pong")
    }))
    defer srv.Close()

    res, err := srv.Client().Get(srv.URL)
    if err != nil { t.Fatal(err) }
    defer res.Body.Close()

    body, _ := io.ReadAll(res.Body)
    if string(body) != "pong" { t.Errorf("body = %q; want pong", body) }
}
```
区别：

| 方式 | 是否走网络 | 适合 |
|------|------------|------|
| `NewRecorder` | 否 | 单个 Handler、路由、中间件 |
| `NewServer` | 是（本地回环） | 客户端代码、超时、重定向、真实协议行为 |

## 14.9 mock：隔离外部依赖
### 14.9.1 接口 + 手写 fake（首选）
业务代码依赖接口，测试时传入假实现：
```go
type User struct {
    ID   int
    Name string
}

var ErrUserNotFound = errors.New("user not found")

type UserRepository interface {
    FindByID(ctx context.Context, id int) (*User, error)
}

type UserService struct {
    repo UserRepository
}

func (s *UserService) GetName(ctx context.Context, id int) (string, error) {
    u, err := s.repo.FindByID(ctx, id)
    if err != nil {
        return "", err
    }
    return u.Name, nil
}
```
fake：
```go
type fakeUserRepo struct {
    users map[int]*User
    err   error
}

func (f *fakeUserRepo) FindByID(ctx context.Context, id int) (*User, error) {
    if f.err != nil {
        return nil, f.err
    }
    u, ok := f.users[id]
    if !ok {
        return nil, ErrUserNotFound
    }
    return u, nil
}
```
测试：
```go
func TestGetName(t *testing.T) {
    repo := &fakeUserRepo{users: map[int]*User{1: {ID: 1, Name: "张三"}}}
    svc := &UserService{repo: repo}

    got, err := svc.GetName(context.Background(), 1)
    if err != nil { t.Fatalf("GetName(1) error: %v", err) }
    if got != "张三" { t.Errorf("GetName(1) = %q; want %q", got, "张三") }

    _, err = svc.GetName(context.Background(), 99)
    if !errors.Is(err, ErrUserNotFound) { t.Errorf("GetName(99) error = %v; want ErrUserNotFound", err) }
}
```
手写 fake 的优点：无依赖、可读、行为完全可控。**接口越小，fake 越好写**，这也是第 07 章「小接口原则」的实践价值。

### 14.9.2 `testify/mock` 简介
需要记录调用次数、参数匹配、统一断言时，可以用 `testify`：
```powershell
go get github.com/stretchr/testify
```
```go
import "github.com/stretchr/testify/mock"

type MockUserRepository struct {
    mock.Mock
}

func (m *MockUserRepository) FindByID(ctx context.Context, id int) (*User, error) {
    args := m.Called(ctx, id)
    user, _ := args.Get(0).(*User)
    return user, args.Error(1)
}

func TestGetNameWithMock(t *testing.T) {
    repo := new(MockUserRepository)
    repo.On("FindByID", mock.Anything, 1).
        Return(&User{ID: 1, Name: "张三"}, nil)

    svc := &UserService{repo: repo}
    got, err := svc.GetName(context.Background(), 1)
    if err != nil { t.Fatal(err) }
    if got != "张三" { t.Errorf("got %q; want 张三", got) }

    repo.AssertExpectations(t)
}
```
常见 API：

- `On("方法名", 参数...)` 声明期望；
- `Return(...)` 指定返回值；
- `mock.Anything` 匹配任意参数；
- `args.Get(0)` / `args.Error(1)` 取返回值；
- `AssertExpectations(t)` 检查期望是否都发生；
- `AssertNotCalled`、`Once`、`Times(n)` 控制调用次数。

`testify` 还有 `assert` 和 `require` 包：`assert.Equal(t, want, got)` 失败继续，`require.NoError(t, err)` 失败立即停止。团队统一用一种风格即可。

> 优先用接口 + fake；只有交互复杂、期望很多时再引入 mock 框架。不要为了让测试能跑而把接口拆得过大。

## 14.10 `go vet` 与 `staticcheck`
### 14.10.1 `go vet`
```powershell
go vet ./...
```
`go vet` 检查编译器不报、但很可能是 bug 的代码，例如：
```go
fmt.Printf("%d\n", "hello")
```
诊断类似：
```
main.go:6:14: fmt.Printf format %d has arg "hello" of wrong type string
```
常见检查：

- `Printf` 格式串与参数不匹配；
- 结构体标签拼写错误；
- `context.WithCancel` 的 `cancel` 未调用（lostcancel）；
- 锁被复制（copylocks）；
- 不可能执行到的代码；
- 错误的 `errors.As` 用法。

`go test` 会自动运行一部分高置信度的 vet 检查，但 CI 里仍应显式执行 `go vet ./...`。

### 14.10.2 `staticcheck`
`staticcheck` 是第三方静态分析工具，检查范围比 `go vet` 更广：
```powershell
go install honnef.co/go/tools/cmd/staticcheck@latest
staticcheck ./...
```
它能发现：

- 无用代码、无用变量；
- 可以简化的写法；
- 错误的 API 用法；
- 可疑的并发与错误处理；
- 过时的标准库用法。

也可以只跑某些检查：`staticcheck -checks=SA1000 ./...`。

静态分析不能替代测试：它只能证明「没发现某类问题」，不能证明业务正确。

## 14.11 Delve 调试
Delve 是 Go 的调试器：
```powershell
go install github.com/go-delve/delve/cmd/dlv@latest
```
安装后在 `%GOPATH%\bin`（通常是 `C:\Users\<你>\go\bin`）下。

### 14.11.1 `dlv debug`
在模块目录执行：
```powershell
dlv debug
```
Delve 会编译带调试信息的程序并进入交互界面：
```
(dlv) break main.main
Breakpoint 1 set at 0x... for main.main() ./main.go:5
(dlv) continue
> main.main() ./main.go:5 (hits goroutine(1):1 total:1)
(dlv) next
(dlv) print name
(dlv) locals
(dlv) step
(dlv) goroutines
(dlv) stack
(dlv) continue
(dlv) quit
```
常用命令：

| 命令 | 作用 |
|------|------|
| `break main.go:12` | 在文件行号打断点 |
| `break main.main` | 在函数入口打断点 |
| `continue` / `c` | 继续运行到下一个断点 |
| `next` / `n` | 单步，不进入函数 |
| `step` / `s` | 单步，进入函数 |
| `stepout` | 跳出当前函数 |
| `print x` / `p x` | 打印变量 |
| `locals` | 打印当前局部变量 |
| `args` | 打印函数参数 |
| `goroutines` | 列出所有 goroutine |
| `stack` | 查看调用栈 |
| `quit` / `q` | 退出 |

调试带参数的程序：
```powershell
dlv debug -- --port 8080
```
调试子目录的 main 包：
```powershell
dlv debug ./cmd/api
```
### 14.11.2 `dlv test`
调试测试：
```powershell
dlv test ./calc
```
```
(dlv) break TestAdd

(dlv) continue
(dlv) next
(dlv) print got
(dlv) quit
```

### 14.11.3 远程/IDE 调试
`dlv debug --headless --listen=:2345 --api-version=2 --accept-multiclient` 可供 VS Code Go 插件、GoLand 连接；日常本地调试直接用 `dlv debug` 即可。

## 14.12 数据竞争与 `-race`
```go
func TestRace(t *testing.T) {
    count := 0
    var wg sync.WaitGroup

    for i := 0; i < 2; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for j := 0; j < 1000; j++ {
                count++
            }
        }()
    }

    wg.Wait()
    t.Log(count)
}
```
运行：
```powershell
go test -race -run TestRace -count=1
```
输出类似：
```
WARNING: DATA RACE
Write at 0x... by goroutine 8:
  main.TestRace.func1() .../race_test.go:12
Previous write at 0x... by goroutine 7:
  main.TestRace.func1() .../race_test.go:12
--- FAIL: TestRace (0.00s)
```
两个 goroutine 同时读写 `count`，没有任何同步，就是数据竞争。

修复方式：
```go
var mu sync.Mutex
mu.Lock()
count++
mu.Unlock()
```
或者用 `atomic.Int64`：
```go
var count atomic.Int64
count.Add(1)
```
要点：

- `-race` 只报告**运行时真正发生**的竞争，没报不代表没有；
- 竞争检测会降低速度、增加内存；
- CI 中可以单独跑一轮 `go test -race ./...`；
- 数据竞争（data race）和业务竞态（race condition）不是一回事：前者是内存访问未同步，后者是时序导致业务结果不确定；
- 某些平台开启 `-race` 需要 cgo。若报 `-race requires cgo`，设置 `CGO_ENABLED=1` 并安装 C 编译器（Windows 常用 mingw-w64），再用 `gcc --version` 验证。

## 14.13 测试组织与 Gin/GORM 测试思路
### 14.13.1 命名与目录
| 类型 | 命名 | 说明 |
|------|------|------|
| 单元测试 | `TestXxx` | 与被测代码同目录 |
| 基准测试 | `BenchmarkXxx` | 同上 |
| 示例测试 | `ExampleXxx` | 同上 |
| 集成测试 | `TestXxx` + build tag | 如 `//go:build integration` |

集成测试示例：
```go
//go:build integration

package repo

func TestUserRepo_MySQL(t *testing.T) { /* ... */ }
```
运行：
```powershell
go test -tags=integration ./...
```
这样默认 `go test ./...` 不会依赖外部数据库。

### 14.13.2 Gin Handler 测试
```go
func setupRouter() *gin.Engine {
    gin.SetMode(gin.TestMode)
    r := gin.New()
    r.GET("/users/:id", func(c *gin.Context) {
        c.JSON(http.StatusOK, gin.H{"id": c.Param("id")})
    })
    return r
}

func TestGetUser(t *testing.T) {
    r := setupRouter()

    w := httptest.NewRecorder()
    req := httptest.NewRequest(http.MethodGet, "/users/42", nil)
    r.ServeHTTP(w, req)

    if w.Code != http.StatusOK { t.Fatalf("status = %d; want %d", w.Code, http.StatusOK) }

    var body map[string]string
    if err := json.Unmarshal(w.Body.Bytes(), &body); err != nil { t.Fatal(err) }
    if body["id"] != "42" { t.Errorf("id = %q; want 42", body["id"]) }
}
```
`gin.SetMode(gin.TestMode)` 会关闭调试输出。`r.ServeHTTP` 让 Gin 走完整的路由与中间件链，比直接调用 handler 更接近真实请求。

### 14.13.3 GORM 测试
思路一：SQLite 内存库。
```go
func newTestDB(t *testing.T) *gorm.DB {
    t.Helper()
    db, err := gorm.Open(sqlite.Open("file::memory:?cache=shared"), &gorm.Config{})
    if err != nil {
        t.Fatal(err)
    }
    if err := db.AutoMigrate(&User{}); err != nil {
        t.Fatal(err)
    }
    return db
}
```
注意：

- `:memory:` 数据库默认只存在于单个连接；连接池可能新建连接导致「表不存在」。可以 `sqlDB.SetMaxOpenConns(1)`，或使用命名共享缓存；
- 多个测试共享同一个内存库会互相污染，最好每个测试用独立 DSN 或事务回滚；
- `gorm.io/driver/sqlite` 在 Windows 上通常需要 CGO；纯 Go 方案可用 `modernc.org/sqlite` 或 `glebarez/sqlite`。

思路二：每个测试用事务回滚。
```go
func TestCreateUser(t *testing.T) {
    db := newTestDB(t)

    tx := db.Begin()
    t.Cleanup(func() { tx.Rollback() })

    if err := tx.Create(&User{Name: "张三"}).Error; err != nil {
        t.Fatal(err)
    }

    var got User
    if err := tx.First(&got, "name = ?", "张三").Error; err != nil {
        t.Fatal(err)
    }
    if got.Name != "张三" {
        t.Errorf("name = %q; want 张三", got.Name)
    }
}
```
思路三：只验证 SQL 用 `DryRun`。
```go
stmt := db.Session(&gorm.Session{DryRun: true}).
    Where("id = ?", 1).First(&User{}).Statement
fmt.Println(stmt.SQL.String()) // SELECT * FROM `users` WHERE id = ? ORDER BY `users`.`id` LIMIT ?
```
### 14.13.4 测试分层
handler 测状态码、JSON、参数校验与中间件（`httptest` + fake service）；service 测业务规则与错误映射（fake repository）；repository 测 SQL、事务与 GORM 标签（SQLite/测试库）；集成测试测整条链路（真实数据库 + 路由）。

单元测试多、集成测试少，保持快反馈；关键路径必须有一条从 HTTP 到数据库的集成测试。

## 14.14 常见错误与陷阱
| 现象 | 原因 | 修复 |
|------|------|------|
| 子 goroutine 里 `t.Fatal` 后测试挂起 | `FailNow` 只能退出当前 goroutine | 用 `t.Errorf` 并 `return`，或把错误传回主 goroutine |
| `t.Setenv` 与 `t.Parallel` 冲突 | 环境变量是进程级共享 | 不要同时使用 |
| 测试单独跑通过、全量跑失败 | 共享全局状态/顺序依赖 | 每个测试独立初始化，`Cleanup` 复位 |
| 修改代码后测试没变化 | 命中了测试缓存 | `-count=1` |
| Benchmark 每次结果差异大 | 准备数据在循环里/机器负载 | 数据放循环外，`ResetTimer`，多跑几次 |
| Benchmark 显示 0.3 ns/op | 编译器优化掉了计算 | 把结果写入包级变量 |
| Example 测试失败 | `// Output:` 与实际输出不完全一致 | 逐字比对空格和换行 |
| `httptest` 测试通过但线上 404 | 只调了 handler，没走路由 | 用 `mux.ServeHTTP` 或 `router.ServeHTTP` |
| mock 没验证期望 | 忘记 `AssertExpectations` | 测试末尾调用 |
| `-race` 没报错就以为没问题 | 只检测实际执行到的竞争 | 增加并发覆盖，代码审查同步逻辑 |
| 覆盖率 100% 但线上有 bug | 覆盖不等于断言正确 | 检查断言质量与边界 |
| 用 `time.Sleep` 等 goroutine | 时序不稳定、慢 | 用 channel、`WaitGroup`、`Eventually` |
| 循环里 `defer` 堆积 | 函数结束才执行 | 抽成独立函数或用 `t.Cleanup` |

### 14.14.1 不要在子 goroutine 里调用 `t.Fatalf`
`t.Fatalf` 内部的 `FailNow` 只会退出当前 goroutine，测试可能继续跑甚至死锁。正确做法是把错误传回测试 goroutine：

```go
errCh := make(chan error, 1)
go func() { errCh <- doWork() }()
if err := <-errCh; err != nil { t.Fatal(err) }
```
### 14.14.2 测试不要依赖执行顺序
Go 不保证测试函数的执行顺序，也不保证包之间顺序。每个测试都应能单独运行：
```powershell
go test -run 'TestCreateUser$' -count=1
```
如果单独跑失败、全量跑通过，说明测试之间有隐式依赖。

### 14.14.3 浮点数不要直接相等比较
```go
// 可能失败
if got != 0.3 { ... }

// 正确
if math.Abs(got-0.3) > 1e-9 { ... }
```
### 14.14.4 `httptest.NewRecorder` 不是完整服务器
它不会做真实网络握手，也不会处理连接复用；`RemoteAddr` 只是 `httptest.NewRequest` 填入的固定测试值。测客户端超时、重定向、TLS 时用 `httptest.NewServer`，或者用真实测试环境。

## 14.17 本章小结

| 主题 | 核心结论 | 易错点 |
|------|----------|--------|
| `go test` | 约定优于配置，测试文件不进入正常构建 | 忘记 `-count=1`，误以为代码没生效 |
| 表驱动 | 用例与逻辑分离 | 失败信息缺少输入与期望 |
| 子测试 | `t.Run` 隔离命名，可单独运行 | 共享可变状态 |
| `t.Helper` | 失败行号指向调用方 | 辅助函数忘记调用 |
| `t.Cleanup` | LIFO，测试结束自动执行 | 与 `defer` 混用导致顺序混乱 |
| `t.TempDir` | 唯一临时目录，自动删除 | 手动清理、路径冲突 |
| 覆盖率 | 语句执行比例 | 把 100% 当成正确性证明 |
| Benchmark | `b.N` 自动调整，报告耗时与分配 | 准备数据放进循环、结果被优化 |
| Example | 文档即测试，逐字比对输出 | 空格/换行不一致 |
| `httptest` | Recorder 测 Handler，Server 测客户端 | 只测 handler 没测路由 |
| mock | 小接口 + fake 优先 | 接口过大、忘记断言期望 |
| `go vet` | 编译器之外的常见错误 | 以为 `go test` 已覆盖全部检查 |
| staticcheck | 更广的静态分析 | 把它当成测试替代品 |
| Delve | 断点、单步、变量、goroutine | 生产环境直接调试 |
| `-race` | 运行时检测数据竞争 | 没报错就以为并发安全 |
| Gin 测试 | `ServeHTTP` 走完整链路 | 忘记 `gin.TestMode` |
| GORM 测试 | SQLite 内存库/事务回滚 | 内存库连接不共享、数据互相污染 |
