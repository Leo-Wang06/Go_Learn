## 15.1 目录结构：先能跑，再谈分层

### 15.1.1 从小项目开始

一个刚起步的 CLI 或小服务，`go.mod` + `main.go` + `main_test.go` 就够了。出现这些信号再拆包：`main.go` 里 SQL、HTTP、业务规则混在一起；多个命令需要共享代码；测试需要替换数据库；多人开始在同一批文件上冲突。

### 15.1.2 一个够用的 Web 服务结构

第 16 章的实战项目采用这个结构：

```
mini-api/
├── go.mod
├── cmd/api/main.go                    # 入口：配置、组装、启动/关闭
├── internal/
│   ├── config/config.go               # 配置加载与校验
│   ├── httpapi/handler.go             # 路由与 Handler
│   ├── httpapi/middleware.go          # 日志、恢复、CORS、TraceID
│   ├── httpapi/response.go            # 统一 JSON 响应
│   ├── service/user_service.go        # 业务规则
│   ├── repository/user_repository.go  # SQL / 存储
│   ├── model/user.go                  # 领域类型与领域错误
│   └── database/database.go           # 连接池与迁移
├── migrations/001_init.sql
└── api/openapi.yaml                   # 接口契约（可选）
```

| 目录 | 职责 | 不该放什么 |
|------|------|------------|
| `cmd/` | 可执行程序入口 | 业务逻辑、SQL |
| `internal/` | 私有实现 | 供外部模块复用的库 |
| `api/` | OpenAPI、proto、接口契约 | Go 业务代码 |
| `migrations/` | 数据库迁移脚本 | 运行时业务逻辑 |

### 15.1.3 `cmd/` 与 `internal/`

`cmd/api/main.go` 的包名仍是 `main`，构建命令是 `go build -o bin/api ./cmd/api`。以后要加定时任务，就再加 `cmd/worker/main.go`，两个 `main` 包共享 `internal/` 下的代码。

`main.go` 应该薄：解析配置、创建依赖、启动服务、等待信号。它不写 SQL，也不做业务判断。

`internal/` 是编译器强制的边界：

> 路径中包含 `internal` 的包，只能被以 `internal` 的父目录为根的代码导入。

模块是 `example.com/shop` 时，`example.com/shop/cmd/api` 可以导入 `example.com/shop/internal/user`；另一个模块 `example.com/other` 导入会编译失败：

```
use of internal package example.com/shop/internal/user not allowed
```

它是编译期约束，不是安全机制。

### 15.1.4 `pkg/`、`api/`、`config/`、`migrations/`

- `pkg/`：没有编译期特殊含义，只是「可被外部导入的公共包」的约定。没有外部使用者时不要创建。
- `api/`：放 OpenAPI/Swagger、protobuf、JSON schema，是接口契约，不是 Go 包。
- `config/`：配置结构体较大时独立成包；小型项目放 `internal/config` 即可。
- `migrations/`：按序号命名的 SQL，例如 `001_init.sql`。生产环境通常配合 golang-migrate、goose、Atlas 等工具。

### 15.1.5 不过度设计

`domain/aggregate`、`application/command`、`infrastructure/persistence`、`interfaces/rest` 这种结构在小项目里通常是负担。DDD 没有错，但成本是更多包、接口、映射和文件。判断标准：这个包有明确职责吗？有两个以上真实使用者吗？拆开后测试更容易，还是只是文件更多？答不上来就先不拆。

### 15.1.6 与 TypeScript 对照

TS 的 `src/` 对应模块根目录；`src/routes/`、`src/services/` 对应 `internal/httpapi/`、`internal/service/`；`tsconfig.json` 的 `paths` 别名在 Go 里没有对应物，直接写模块路径；TS 的 `@internal` 只是约定，Go 的 `internal/` 是编译器强制。

## 15.2 命名规范

### 15.2.1 包名与变量名

包名小写、简短、单数，不用下划线：

```go
package user         // 好
package user_service // 不好
package UserService  // 违反惯例
```

调用处不要重复包名：`user.NewService()` 好于 `user.NewUserService()`。

变量名作用域越小可以越短：循环里用 `i, v`，短函数里用 `u, err`，包级变量写清楚 `defaultHTTPClient`。社区已接受的缩写只有 `ctx`、`err`、`db`、`id`、`URL`、`HTTP`、`JSON` 等。

### 15.2.2 接口命名：一个方法用 `-er`

```go
type Reader interface { Read(p []byte) (n int, err error) }
type UserStore interface { GetByID(ctx context.Context, id int64) (*User, error) }
```

| 方法 | 接口名 |
|------|--------|
| `Read` | `Reader` |
| `Write` | `Writer` |
| `Close` | `Closer` |
| `ServeHTTP` | `http.Handler` |

不要写 `IUserService`、`UserServiceInterface`。接口定义在**使用方**：

```go
// service 包：我需要一个能查用户的东西
type UserRepository interface {
    GetByID(ctx context.Context, id int64) (*model.User, error)
}
```

依赖方向变成「service → 接口 ← repository」，repository 不需要知道 service 需要什么。

### 15.2.3 错误命名：`ErrXxx` 与 `XxxError`

```go
var (
    ErrNotFound = errors.New("not found")
    ErrConflict = errors.New("conflict")
)

type ValidationError struct {
    Field   string
    Message string
}

func (e *ValidationError) Error() string { return e.Field + ": " + e.Message }
```

`ErrNotFound` 是拿来 `errors.Is` 比较的值；`ValidationError` 是拿来 `errors.As` 提取的类型。

### 15.2.4 缩写与重复

```go
// 好
userID
httpClient
parseURL
JSONEncoder

// 不好
userId
parseUrl
JsonEncoder
```

包名已表达的信息，标识符里不要重复：`user.Service` 好于 `user.UserService`。常量用 `MaxRetries`，不用 `MAX_RETRIES`；测试函数用 `TestCreateUser`。

## 15.3 注释规范

### 15.3.1 包注释与导出标识符

包注释放在 `package` 上方，以 `Package xxx` 开头：

```go
// Package user 提供用户的创建、查询和校验逻辑。
//
// 该包不直接访问 HTTP，也不负责 JSON 编解码。
package user
```

导出的类型、函数、方法、常量、变量都要有注释，并以标识符名字开头：

```go
// Service 处理用户相关的业务规则。
type Service struct {
    repo UserRepository
}

// Create 校验输入并创建用户。
//
// 如果邮箱已存在，返回 ErrConflict。
func (s *Service) Create(ctx context.Context, in CreateUserInput) (*User, error) { ... }
```

好的注释回答：为什么这样做、有什么约束、会返回哪些错误、是否并发安全、参数单位是什么。不要写「Create 创建用户」这种同义反复。

### 15.3.2 `TODO` / `FIXME` 与废弃标记

```go
// TODO(alice): 支持按邮箱模糊搜索，等产品确认需求后再做。
// FIXME(bob): 这里并发下会重复插入，需要加唯一索引。

// Deprecated: 使用 NewServiceWithLogger 代替。
func NewService(repo UserRepository) *Service { ... }
```

`TODO` 要有负责人和条件；`Deprecated:` 会被 `go doc` 和 IDE 标记。

## 15.4 错误处理规范

### 15.4.1 错误的四个层次

| 层次 | 职责 | 例子 |
|------|------|------|
| 产生 | 返回原始错误，附加上下文 | `fmt.Errorf("insert user: %w", err)` |
| 翻译 | 底层错误转成领域错误 | 唯一键冲突 → `ErrConflict` |
| 决策 | 根据错误决定流程 | service 返回业务错误 |
| 呈现 | 转成 HTTP 状态码、日志 | handler：`ErrNotFound` → 404 |

同一个错误不应该在每一层都记录日志。日志只在**边界**记录一次。

### 15.4.2 包装：用 `%w` 保留错误链

```go
var ErrNotFound = errors.New("not found")

func findUser(id int64) error {
    return fmt.Errorf("find user %d: %w", id, ErrNotFound)
}

func main() {
    err := findUser(7)
    fmt.Println(err)                            // find user 7: not found
    fmt.Println(errors.Is(err, ErrNotFound))    // true
}
```

- `%w` 保留错误链，`errors.Is` / `errors.As` 才能工作；
- `%v` 只转成字符串，错误链断了；
- 包装时补充「做什么时失败」。

### 15.4.3 `errors.Is` 与 `errors.As`

`errors.Is` 判断是不是某个哨兵错误；不要用 `err == ErrNotFound`，因为错误可能被包装过多层。

```go
type ValidationError struct {
    Field   string
    Message string
}

func (e *ValidationError) Error() string { return e.Field + ": " + e.Message }

var ve *ValidationError
if errors.As(err, &ve) {
    fmt.Println("field:", ve.Field)     // field: name
    fmt.Println("message:", ve.Message) // message: name is required
}
```

`errors.As` 的第二个参数必须是指向错误类型的指针，`&ve` 的类型是 `**ValidationError`。

### 15.4.4 错误信息风格与日志边界

```go
// 好：小写开头，没有句号，包含上下文
fmt.Errorf("load config: %w", err)
fmt.Errorf("query user %d: %w", id, err)

// 不好：大写开头、句号结尾、重复 "error"
fmt.Errorf("Error: Failed to load config.")
```

不要记录后又返回：

```go
// 不好：日志重复，调用方还会再记一次
if err != nil {
    log.Printf("query failed: %v", err)
    return nil, err
}

// 好：repository 只包装返回，handler 统一记录并决定状态码
return nil, fmt.Errorf("query user %d: %w", id, err)
```

### 15.4.5 什么时候可以 panic

`panic` 只用于「程序无法继续」：初始化时配置缺失、端口被占用；不可能发生的编程错误；测试辅助函数。

不要用 `panic` 处理用户输入错误、记录不存在、数据库超时。Web 服务的 recover 中间件是最后防线，不是错误处理策略。

## 15.5 配置：环境变量、flag、配置文件

### 15.5.1 环境变量与 `flag`

读取环境变量用 `os.Getenv("APP_ADDR")`，未设置时得到空字符串，可以回退到默认值。区分「未设置」和「设置为空」用 `os.LookupEnv`：`if value, ok := os.LookupEnv("APP_ADDR"); ok { ... }`。

Go 标准库没有自动加载 `.env` 的功能。容器和云平台通常直接注入环境变量。

`flag` 适合命令行参数：

```go
addr := flag.String("addr", ":8080", "HTTP listen address")
timeout := flag.Duration("shutdown-timeout", 10*time.Second, "shutdown timeout")
debug := flag.Bool("debug", false, "enable debug logs")
flag.Parse()
```

运行 `go run . -addr :9090 -shutdown-timeout 5s -debug` 后，三个指针分别指向 `:9090`、`5s`、`true`。默认值会出现在 `-h` 输出里。

### 15.5.2 配置文件

配置文件适合放一组结构化配置。为不引入 YAML 依赖，这里用标准库 `encoding/json`：

```json
{
  "addr": ":9090",
  "dsn": "file:from-file.db",
  "timeout": "5s"
}
```

```go
type fileConfig struct {
    Addr    string `json:"addr"`
    DSN     string `json:"dsn"`
    Timeout string `json:"timeout"`
}
```

生产项目常用 YAML，需要引入 `gopkg.in/yaml.v3`，思路相同。

### 15.5.3 优先级：flag > 环境变量 > 文件 > 默认值

```go
func Load() (Config, error) {
    configPath := flag.String("config", "", "JSON config path")
    addrFlag := flag.String("addr", "", "listen address")
    flag.Parse()

    // 1. 默认值
    cfg := Config{Addr: ":8080", DSN: "file:app.db", Timeout: 10 * time.Second}

    // 2. 文件
    if *configPath != "" {
        raw, err := os.ReadFile(*configPath)
        if err != nil {
            return Config{}, fmt.Errorf("read config: %w", err)
        }
        var fc fileConfig
        if err := json.Unmarshal(raw, &fc); err != nil {
            return Config{}, fmt.Errorf("parse config: %w", err)
        }
        if fc.Addr != "" {
            cfg.Addr = fc.Addr
        }
        if fc.DSN != "" {
            cfg.DSN = fc.DSN
        }
        if fc.Timeout != "" {
            d, err := time.ParseDuration(fc.Timeout)
            if err != nil {
                return Config{}, fmt.Errorf("config timeout: %w", err)
            }
            cfg.Timeout = d
        }
    }

    // 3. 环境变量
    if v := os.Getenv("APP_ADDR"); v != "" {
        cfg.Addr = v
    }
    if v := os.Getenv("APP_DSN"); v != "" {
        cfg.DSN = v
    }
    if v := os.Getenv("APP_TIMEOUT"); v != "" {
        d, err := time.ParseDuration(v)
        if err != nil {
            return Config{}, fmt.Errorf("APP_TIMEOUT: %w", err)
        }
        cfg.Timeout = d
    }

    // 4. flag 覆盖
    if *addrFlag != "" {
        cfg.Addr = *addrFlag
    }
    return cfg, nil
}
```

配置结构体 `Config` 含 `Addr`、`DSN`、`Timeout` 三个字段。验证四种来源：

```bash
go run .                                             # 默认值
go run . -config dev.json                            # 文件
APP_ADDR=:7070 go run . -config dev.json             # 环境变量覆盖文件
APP_ADDR=:7070 go run . -config dev.json -addr :6060 # flag 覆盖环境变量
```

输出依次是 `:8080/file:app.db/10s`、`:9090/file:from-file.db/5s`，以及两次 `:7070` 和 `:6060` 的覆盖结果。PowerShell 用 `$env:APP_ADDR = ":7070"` 设置环境变量。

### 15.5.4 校验与密钥

加载后立刻校验：`Addr` 不能为空，`Timeout` 必须大于 0。配置缺失应该在启动时失败，而不是等第一个请求进来才报错。

密钥不要写进配置文件并提交：

```go
// 不好
dsn := "user:password@tcp(db:3306)/app"

// 好
dsn := os.Getenv("APP_DB_DSN")
```

`.env` 只用于本地开发，并加入 `.gitignore`；生产环境使用平台的密钥管理。

## 15.6 结构化日志与 TraceID

### 15.6.1 从 `log` 到 `log/slog`

`log.Printf("user %d created", 42)` 输出一行文本，机器难以解析。`log/slog` 支持结构化键值对：

```go
logger.Info("user created", "user_id", 42, "email", "alice@example.com")
```

JSON 输出：

```json
{"time":"2026-10-18T12:00:00.000+08:00","level":"INFO","msg":"user created","user_id":42,"email":"alice@example.com"}
```

生产环境通常用 JSON，方便日志平台检索。键名保持稳定、简短、可检索，不要拼接字符串：

```go
// 不好：日志平台无法按 user_id 过滤
logger.Info(fmt.Sprintf("user %d created", 42))

// 好
logger.Info("user created", "user_id", 42)
```

### 15.6.2 日志级别

`DEBUG` 用于开发排查细节；`INFO` 记录正常业务事件（启动、请求完成）；`WARN` 表示可恢复异常（重试、降级、慢查询）；`ERROR` 表示需要人处理的失败（数据库不可用、未预期错误）。

```go
var level slog.Level
if err := level.UnmarshalText([]byte("INFO")); err != nil {
    return err
}
logger := slog.New(slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{Level: level}))
```

`UnmarshalText` 接受 `DEBUG`、`INFO`、`WARN`、`ERROR`（大小写不敏感）。

### 15.6.3 TraceID：把一次请求的日志串起来

1. 入口中间件读取 `X-Request-ID`，没有就生成；
2. 放进 `context.Context`；
3. 每条日志带上 `trace_id`；
4. 调用下游时继续传 `X-Request-ID`。

```go
type ctxKey string

const traceIDKey ctxKey = "trace_id"

func withTraceID(ctx context.Context, id string) context.Context {
    return context.WithValue(ctx, traceIDKey, id)
}

func traceIDFrom(ctx context.Context) string {
    id, _ := ctx.Value(traceIDKey).(string)
    return id
}
```

使用时：

```go
logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))
ctx := withTraceID(context.Background(), "req-7f3a")
logger.InfoContext(ctx, "user created", "user_id", 42, "trace_id", traceIDFrom(ctx))
```

输出中会包含 `"trace_id":"req-7f3a"`。注意：`InfoContext` **不会自动**从 context 取 TraceID。slog 默认只把 context 传给 Handler，是否提取取决于 Handler 实现。上面的写法是手动取出后作为字段传入，最直观。

### 15.6.4 TraceID 中间件

```go
func RequestID(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        id := r.Header.Get("X-Request-ID")
        if id == "" {
            var b [16]byte
            if _, err := rand.Read(b[:]); err == nil {
                id = hex.EncodeToString(b[:])
            } else {
                id = strconv.FormatInt(time.Now().UnixNano(), 10)
            }
        }
        w.Header().Set("X-Request-ID", id)
        ctx := context.WithValue(r.Context(), traceIDKey, id)
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}
```

Gin 中同理：用 `c.GetHeader` 读取、`c.Set("trace_id", id)` 保存、`c.Request = c.Request.WithContext(...)` 注入。`c.Next()` 的用法在第 17 章展开。

### 15.6.5 日志规范

- 不记录密码、token、完整身份证号、完整银行卡号；
- 不记录整个请求体，除非确认没有敏感字段；
- 同一个错误只在边界记录一次；
- 请求日志包含 method、path、status、duration、trace_id；
- 慢请求用 `WARN`，5xx 用 `ERROR`，4xx 通常用 `INFO`；
- 字段名不要频繁改，否则历史查询会断。

Gin 自带的 `gin.Logger()` 输出固定格式文本。生产项目通常自己写 `slog` 中间件，把请求日志和业务日志统一输出。

## 15.7 优雅关闭

直接 kill 进程会导致正在处理的请求被中断、响应写一半、事务未提交、连接池未关闭。优雅关闭的步骤：停止接收新连接 → 等待活跃请求 → 超时强制退出 → 关闭数据库等资源。

### 15.7.1 `signal.NotifyContext` 与 `Shutdown`

```go
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer stop()
```

- `os.Interrupt` 对应 Ctrl+C；
- `syscall.SIGTERM` 对应容器编排系统的终止信号；
- 收到信号后 `ctx.Done()` 被关闭；
- `stop()` 释放监听资源，应该 `defer`。

```go
shutdownCtx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()

if err := srv.Shutdown(shutdownCtx); err != nil {
    return fmt.Errorf("shutdown: %w", err)
}
```

`Shutdown(ctx)` 关闭监听器并等待活跃请求结束；`Close()` 立即关闭所有连接。`Shutdown` 超时返回 `context.DeadlineExceeded`，且不会关闭 hijacked 连接（例如 WebSocket）。Windows 上 `SIGTERM` 常量存在，但实际能否收到取决于环境；Ctrl+C 一定可用。

### 15.7.2 完整示例

```go
func main() {
    ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
    defer stop()

    if err := run(ctx); err != nil {
        log.Fatal(err)
    }
}

func run(ctx context.Context) error {
    mux := http.NewServeMux()
    mux.HandleFunc("GET /", func(w http.ResponseWriter, r *http.Request) {
        fmt.Fprintln(w, "hello")
    })

    srv := &http.Server{Addr: "127.0.0.1:18090", Handler: mux, ReadHeaderTimeout: 5 * time.Second}

    errCh := make(chan error, 1)
    go func() {
        log.Println("listening on", srv.Addr)
        if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
            errCh <- err
        }
    }()

    select {
    case err := <-errCh:
        return err
    case <-ctx.Done():
        log.Println("signal received, shutting down")
    }

    shutdownCtx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
    defer cancel()

    if err := srv.Shutdown(shutdownCtx); err != nil {
        return fmt.Errorf("shutdown: %w", err)
    }
    log.Println("server stopped")
    return nil
}
```

启动后按 Ctrl+C，输出类似 `listening on 127.0.0.1:18090`、`signal received, shutting down`、`server stopped`。`Shutdown` 会等待正在处理的请求写完响应再返回。

### 15.7.3 关闭顺序与常见错误

推荐顺序：收到信号 → `Shutdown` 停止接收新请求 → 等待请求完成或超时 → `db.Close()` → 关闭消息队列/Redis → 进程退出。

不要在 `Shutdown` 之前关闭数据库，否则正在处理的请求会拿到 `sql: database is closed`。

```go
// 错误：收到关闭信号时也 log.Fatal
if err := srv.ListenAndServe(); err != nil {
    log.Fatal(err)
}

// 正确
if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
    return err
}

// 错误：Shutdown 没有超时，可能永远卡住
srv.Shutdown(context.Background())
```

## 15.8 依赖注入

### 15.8.1 为什么需要

如果构造函数内部自己 `sql.Open`，测试无法替换数据库、连接无法复用、配置无法传入、依赖关系隐藏在函数体里。

DI 的核心思想：**依赖由外部创建并传入，而不是在内部自己创建**。

### 15.8.2 构造函数注入

```go
type UserRepository struct{ db *sql.DB }

func NewUserRepository(db *sql.DB) *UserRepository { return &UserRepository{db: db} }

type UserService struct{ repo *UserRepository }

func NewUserService(repo *UserRepository) *UserService { return &UserService{repo: repo} }

type UserHandler struct{ svc *UserService }

func NewUserHandler(svc *UserService) *UserHandler { return &UserHandler{svc: svc} }
```

在 `main` 里组装：

```go
db, err := sql.Open("sqlite", os.Getenv("APP_DB_DSN"))
if err != nil {
    log.Fatal(err)
}
defer db.Close()

repo := NewUserRepository(db)
svc := NewUserService(repo)
handler := NewUserHandler(svc)
```

没有反射，没有框架，依赖关系一眼可见。

### 15.8.3 接口放在使用方

```go
// service 包
type UserRepository interface {
    GetByID(ctx context.Context, id int64) (*model.User, error)
    Create(ctx context.Context, user *model.User) error
}

type Service struct{ repo UserRepository }

func NewService(repo UserRepository) *Service { return &Service{repo: repo} }
```

repository 包只要方法集匹配，就自动满足接口。这样 service 可以定义自己需要的最小接口，测试时用 fake 实现。

### 15.8.4 `wire` 简介

依赖变多后，手写组装代码会很长。`wire` 是 Google 的编译期依赖注入工具：你声明「需要什么」，它生成「怎么创建」。

```bash
go install github.com/google/wire/cmd/wire@latest
```

声明文件（build tag 让它不参与正常编译）：

```go
//go:build wireinject

package main

import (
    "database/sql"
    "github.com/google/wire"
)

func InitUserHandler(db *sql.DB) *UserHandler {
    wire.Build(NewUserRepository, NewUserService, NewUserHandler)
    return nil
}
```

运行 `wire ./...`，生成的 `wire_gen.go` 就是按依赖顺序调用三个构造函数。要点：`wire.Build` 里是提供者函数；wire 根据参数和返回值推导依赖图；生成的是普通 Go 代码，没有运行时反射；依赖缺失或循环时，生成阶段报错。

依赖少于 10 个、团队不熟悉代码生成、项目周期短时，手写构造函数更划算。

## 15.10 工具链

### 15.10.1 `gofmt` 与 `goimports`

```bash
gofmt -l .        # 列出未格式化的文件
gofmt -w .        # 就地格式化
go fmt ./...      # 对模块所有包执行
```

`gofmt` 规则固定，没有配置项，团队不需要争论缩进和换行。

`gofmt` 不管理 import。`goimports` 会删除未使用的 import、自动添加缺失的 import、按组排序：

```bash
go install golang.org/x/tools/cmd/goimports@latest
goimports -w .
```

VS Code 可以把保存时的格式化工具设为 `goimports`。

### 15.10.2 `go vet` 与 `golangci-lint`

```bash
go vet ./...
```

检查 `Printf` 格式串与参数不匹配、结构体标签格式错误、不可达代码、锁被复制、错误的 `sync.WaitGroup` 用法等。

`golangci-lint` 把多个 linter 聚合到一个命令里，适合 CI。安装方式按官方文档选择（二进制、Homebrew、Scoop 或 `go install`）：

```bash
golangci-lint run ./...
```

常用 linter 包括 `errcheck`（未处理错误）、`govet`、`staticcheck`、`ineffassign`、`unused`、`revive`、`gofmt`/`goimports`、`bodyclose`、`sqlclosecheck`。不要一次启用所有 linter，先启用默认集合，再按团队痛点逐个添加。规则太多会让人习惯性忽略警告。

```bash
golangci-lint run --timeout=5m ./...
```

VS Code 可设置保存时用 `goimports` 格式化、用 `golangci-lint` 检查。

## 15.11 构建：版本信息与交叉编译

### 15.11.1 用 `-ldflags` 注入版本

```go
var (
    version   = "dev"
    commit    = "none"
    buildTime = "unknown"
)
```

直接运行输出 `version=dev commit=none buildTime=unknown`。构建时注入：

```bash
go build -ldflags "-X main.version=1.2.3 -X main.commit=abc1234 -X main.buildTime=2026-10-18T12:00:00Z" -o version.exe .
./version.exe
```

输出 `version=1.2.3 commit=abc1234 buildTime=2026-10-18T12:00:00Z`。

`-X` 的格式是 `-X importpath.variable=value`。对于 `main` 包，写 `main.version`。链接器只能修改变量，不能改常量；变量必须是 `string`：

```go
var version = "dev" // 可以
// const version = "dev" // 不可以被 -ldflags 修改
```

CI 中可以把 `git describe --tags --always --dirty`、`git rev-parse --short HEAD`、`date -u` 的结果传给同样的 `-X` 参数。

### 15.11.2 交叉编译

设置 `GOOS` 和 `GOARCH`：

```bash
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -o bin/api-linux-amd64 ./cmd/api
GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build -o bin/api-linux-arm64 ./cmd/api
GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build -o bin/api-windows-amd64.exe ./cmd/api
GOOS=darwin GOARCH=arm64 CGO_ENABLED=0 go build -o bin/api-darwin-arm64 ./cmd/api
```

PowerShell 用 `$env:GOOS = "linux"`、`$env:GOARCH = "amd64"`、`$env:CGO_ENABLED = "0"` 设置，构建后 `Remove-Item Env:GOOS, Env:GOARCH, Env:CGO_ENABLED` 清理。

`go tool dist list` 会列出所有支持的 `os/arch` 组合，例如 `linux/amd64`、`windows/arm64`、`darwin/arm64`。

`CGO_ENABLED=0` 生成静态链接的二进制，部署时不需要系统安装 C 库，也更容易交叉编译；但依赖 C 的库无法使用（例如 `mattn/go-sqlite3` 需要 CGO）。第 16 章使用的 `modernc.org/sqlite` 是纯 Go 实现，因此可以 `CGO_ENABLED=0` 交叉编译。

### 15.11.3 文件名后缀、构建标签与体积

文件名后缀 `_linux.go`、`_windows.go`、`_darwin_arm64.go` 会自动参与构建约束。更复杂的条件用构建标签：

```go
//go:build linux && amd64

package platform
```

构建标签必须放在文件最上方、`package` 之前，且与 `package` 之间空一行。

`go build -ldflags "-s -w"` 去掉符号表和 DWARF 调试信息，体积更小，但 Delve 调试和部分性能分析会受限。

## 15.12 与 Gin/GORM 的关联

Gin 项目通常按 `cmd/api/main.go`、`internal/httpapi/`、`internal/service/`、`internal/repository/`、`internal/model/` 组织。Gin 只负责 HTTP 层，业务逻辑不要写进 handler。

GORM 初始化与连接池：

```go
db, err := gorm.Open(mysql.Open(dsn), &gorm.Config{})
if err != nil {
    return fmt.Errorf("open gorm: %w", err)
}
sqlDB, _ := db.DB()
sqlDB.SetMaxOpenConns(25)
sqlDB.SetMaxIdleConns(25)
sqlDB.SetConnMaxLifetime(5 * time.Minute)
```

GORM 底层仍然是 `database/sql`，连接池参数必须配置。优雅关闭沿用 15.7 的 `Shutdown`，之后再 `sqlDB.Close()`。

Gin handler 中：

```go
func CreateUser(c *gin.Context) {
    ctx := c.Request.Context()
    db.WithContext(ctx).Create(&user)
}
```

GORM 查询带上 context，数据库操作才能响应请求取消和超时。

## 15.13 常见错误与陷阱

| 错误/现象 | 原因 | 修复 |
|-----------|------|------|
| `use of internal package not allowed` | 从 `internal` 父目录之外导入 | 移到模块内部，或改为公开包 |
| 包名带下划线 | 违反 Go 惯例 | 改成小写单词 |
| 接口叫 `IUserService` | 照搬 Java/C# | 用 `UserService` 或 `UserStore` |
| `err == ErrNotFound` 判断失败 | 错误被包装 | 用 `errors.Is` |
| `errors.As` panic | 第二个参数不是指针 | 传 `&target` |
| 日志重复 | 每层都 log 后返回 | 只在边界记录 |
| 配置写死 | 没有外部注入 | 环境变量/flag/文件 |
| 空环境变量被当成未设置 | 用 `Getenv` 无法区分 | 用 `LookupEnv` |
| 日志无法检索 | 字符串拼接 | 键值对 |
| TraceID 丢失 | context 没传下去 | 每层用 `ctx`，日志显式带字段 |
| 进程无法退出 | `Shutdown` 没有超时 | `context.WithTimeout` |
| 关闭时仍报错 | 把 `ErrServerClosed` 当异常 | `errors.Is` 排除 |
| 交叉编译失败 | 依赖 CGO | `CGO_ENABLED=0`，换纯 Go 驱动 |
| `-X` 不生效 | 变量是 `const` 或非 string | 改成包级 `var string` |
| lint 大量报错 | 一次启用太多规则 | 先默认集合，逐步增加 |

补充三点：

1. `internal` 是编译期约束，不是安全机制；
2. `slog.InfoContext` 不会自动读取 TraceID，需要手动加字段或自定义 Handler；
3. `Shutdown` 只等待 HTTP 活跃连接，自己启动的后台 goroutine 需要单独的 context 退出机制。

## 15.16 本章小结

| 主题 | 一句话解释 | 易错点 |
|------|------------|--------|
| `cmd/`、`internal/` | 入口与编译器强制的私有边界 | 不要放业务逻辑、不要越界导入 |
| 命名、注释 | 小写简短、导出以名字开头 | 不要 `I` 前缀、不要同义反复 |
| 错误 | `%w` 包装，边界统一处理 | `%v` 断链、重复日志 |
| 配置 | flag > env > file > default | 不要硬编码、不要提交密钥 |
| 日志 | 结构化键值对 + 级别 | 不要拼接字符串、不要泄密 |
| TraceID | 入口生成，context 传递 | `InfoContext` 不会自动取 |
| 优雅关闭 | `NotifyContext` + `Shutdown` | 记得超时和 `ErrServerClosed` |
| DI、wire | 构造函数注入，main 组装 | 接口放使用方、wire 只生成代码 |
| `gofmt`、`goimports` | 固定格式 + import 管理 | gofmt 不管理 import |
| `golangci-lint` | 聚合 linter | 不要一次全开 |
| `-ldflags` | 链接期注入 string `var` | `const` 改不了 |
| 交叉编译 | `GOOS`/`GOARCH` | CGO 依赖会失败 |
