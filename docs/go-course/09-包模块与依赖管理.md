## 9.1 包、目录与导入路径
### 9.1.1 一个目录一个包
Go 的包由**同一个目录下的 `.go` 文件**组成，这些文件必须声明同一个包名：

```
demo/
├── go.mod
├── main.go          // package main
└── mathutil/
    └── mathutil.go  // package mathutil
```

`go.mod`：

```
module example.com/demo

go 1.22
```

`mathutil/mathutil.go`：

```go
package mathutil

func Add(a, b int) int { return a + b }

// 小写开头，只在 mathutil 包内可见
func sub(a, b int) int { return a - b }
```

`main.go`：

```go
package main

import (
    "fmt"

    "example.com/demo/mathutil"
)

func main() {
    fmt.Println(mathutil.Add(1, 2)) // 3
}
```

输出：

```
3
```

导入路径的规则：

```
导入路径 = 模块路径 + 子目录
example.com/demo + /mathutil = example.com/demo/mathutil
```

### 9.1.2 包名与目录名
包名由 `package` 声明决定，不强制等于目录名（例如目录 `util/` 里可以写 `package helper`），但**惯例是二者一致**。包名要小写、简短、不用下划线或驼峰，避免 `util`、`common`、`base` 这类空泛名字，也不要与标准库冲突。

### 9.1.3 `package main` 是程序入口
- 只有 `package main` 能编译成可执行文件，必须有 `func main()`；
- `package main` 不能被其他包导入，否则报 `is a program, not an importable package`。

同一个目录下的测试文件是唯一常见例外：`foo_test.go` 可以写 `package foo`（内部测试，能访问未导出标识符），也可以写 `package foo_test`（外部测试，只能访问导出标识符）。

## 9.2 `import` 的四种形式
### 9.2.1 普通导入
```go
import (
    "fmt"
    "strings"

    "example.com/demo/mathutil"
)
```

标准库和第三方库分开写是常见风格，`gofmt` 不会自动分组，`goimports` 会。

### 9.2.2 别名导入
```go
import (
    crand "crypto/rand"
    mrand "math/rand"
)
```

解决同名包冲突，或缩短长包名，例如 `import g "github.com/gin-gonic/gin"` 后用 `g.Default()`。别名只影响当前文件，不影响包本身。

### 9.2.3 空白导入 `_`
```go
import _ "github.com/go-sql-driver/mysql"
```

只执行包的 `init`，不使用包内标识符。典型用途是注册驱动：

```go
import (
    "database/sql"
    _ "github.com/go-sql-driver/mysql"
)

db, err := sql.Open("mysql", dsn)
```

`sql.Open` 本身不知道 MySQL 驱动；驱动在 `init` 中调用 `sql.Register("mysql", ...)` 完成注册。没有空白导入，运行时会报 `sql: unknown driver "mysql" (forgotten import?)`。其他用途：`_ "net/http/pprof"` 注册性能分析 handler；`_ "time/tzdata"` 把时区数据库编进二进制。

### 9.2.4 点导入（不推荐）
`import . "fmt"` 后可以直接写 `Println("hello")`，但看不出标识符来自哪个包，容易冲突，代码审查和跳转困难。除了极少数测试或生成代码，不要使用。

### 9.2.5 导入未使用会编译失败
```go
import "strings" // 没有使用会报：imported and not used
```

只想执行副作用时用 `_`；确实不需要就删除。

## 9.3 导出规则
首字母大写 = 导出（其他包可见）；首字母小写 = 包内私有。

```go
package mathutil

func Add(a, b int) int { return a + b } // 导出
func sub(a, b int) int { return a - b } // 包内私有

type User struct {
    Name string // 导出字段
    age  int    // 包内私有字段
}

func (u User) GetName() string { return u.Name } // 导出方法
func (u User) getAge() int     { return u.age }  // 包内私有方法
```

其他包：

```go
mathutil.Add(1, 2) // 可以
// mathutil.sub(1, 2) // 编译错误：cannot refer to unexported name
```

导出规则同样适用于：

- 结构体字段；
- 方法；
- 常量、变量；
- 类型。

这与 Gin/GORM 直接相关：

- GORM 只映射**导出字段**，小写字段会被忽略；
- `encoding/json` 只序列化导出字段；
- Gin 的 `ShouldBindJSON` 也只能写入导出字段。

```go
type User struct {
    Name string `json:"name" gorm:"column:name"`
    age  int    // JSON 和 GORM 都看不到
}
```

导出标识符应该有文档注释，注释以标识符名开头：

```go
// Add 返回 a 与 b 的和。
func Add(a, b int) int { return a + b }
```

## 9.4 `init` 函数
### 9.4.1 语法与执行时机
```go
func init() {
    // 初始化逻辑
}
```

规则：

- 没有参数、没有返回值；
- 不能被显式调用，也不能被引用；
- 一个包可以有多个 `init`，一个文件也可以有多个；
- 执行顺序：先初始化包级变量，再执行 `init`；
- 被导入的包先于导入者初始化；
- 同一个包内多个 `init` 的顺序**通常**按文件名字典序，但不要依赖它。

```go
package main

import "fmt"

var x = initX()

func initX() int {
    fmt.Println("1. 变量初始化")
    return 10
}

func init() {
    fmt.Println("2. init")
}

func main() {
    fmt.Println("3. main", x)
}
```

输出：

```
1. 变量初始化
2. init
3. main 10
```

### 9.4.2 常见用途
- 注册驱动（`database/sql`）；
- 注册指标、编解码器、插件；
- 设置包的默认值；
- 校验编译期常量或配置。

### 9.4.3 风险与建议
- 不要在 `init` 里做网络请求、读大文件、启动 goroutine；
- 不要 `panic`，否则整个程序无法启动且难以测试；
- 不要依赖 `init` 的执行顺序；
- 需要返回错误或需要配置的初始化，改用显式的 `NewXxx` / `Setup` 函数。

> 库代码尤其要克制：导入一个包就产生副作用，会让调用方难以排查。

## 9.5 `internal` 包
`internal` 是 Go 的访问控制机制：**只有位于 `internal` 父目录树内的代码才能导入它**。

目录：

```
example.com/shop/
├── go.mod
├── cmd/
│   └── api/
│       └── main.go
├── internal/
│   └── auth/
│       └── auth.go
└── pkg/
    └── client/
        └── client.go
```

规则：

- `example.com/shop/internal/auth` 可以被 `example.com/shop/...` 下的包导入；
- 不能被 `example.com/other` 导入；
- 规则基于**导入路径**，不是文件系统位置；
- `internal` 可以有多个层级，每层限制各自父目录树。

```go
// example.com/shop/cmd/api/main.go
import "example.com/shop/internal/auth" // 可以
```

```go
// example.com/other/main.go
import "example.com/shop/internal/auth" // 编译错误
```

错误类似：

```
use of internal package example.com/shop/internal/auth not allowed
```

用途：

- 把实现细节锁在模块内部；
- 防止外部用户依赖不稳定的 API；
- 在大型项目中划清边界。

`pkg/` 不是 Go 的保留目录，只是社区习惯，表示「可以给外部用」；它没有强制力。

## 9.6 `go.mod` 详解
一个典型的 `go.mod`：

```
module example.com/shop

go 1.22

require (
    github.com/gin-gonic/gin v1.10.0
    gorm.io/driver/mysql v1.5.6
    gorm.io/gorm v1.25.10
)

require (
    github.com/bytedance/sonic v1.11.6 // indirect
    github.com/gabriel-vasile/mimetype v1.4.3 // indirect
    // ... 其他间接依赖
)

replace example.com/legacy => ../legacy

exclude example.com/broken v1.2.3

retract v1.0.0 // 该版本有严重 bug
```

### 9.6.1 `module`
`module example.com/shop` 声明模块路径，也是其他包导入本模块的前缀。通常是仓库地址或自有域名；发布到公网时路径要能被 `go get` 解析，本地练习可以用 `example.com/...`。

### 9.6.2 `go`
`go 1.22` 声明语言版本，影响循环变量语义、标准库 API 可用性、模块图裁剪等。Go 1.21 起还有可选的 `toolchain` 指令，日常项目通常不需要手写。

### 9.6.3 `require`
`require github.com/gin-gonic/gin v1.10.0` 声明**最低版本**，不是锁定版本。Go 使用 MVS：最终选中的版本是所有要求中的最大值。`// indirect` 表示当前模块没有直接导入，只是被其他依赖带进来；`go mod tidy` 会自动整理。

### 9.6.4 `replace`
`replace example.com/legacy => ../legacy` 把模块替换成另一个路径或本地目录，详见 9.10 节。

### 9.6.5 `exclude`
`exclude example.com/broken v1.2.3` 排除某个依赖版本，Go 会选择另一个可用版本；只对**主模块**的 `go.mod` 生效。

### 9.6.6 `retract`
由模块作者声明「这些版本不要用」：

```
retract (
    v1.0.0
    [v1.1.0, v1.1.5]
)
```

- 只能写在模块自己的 `go.mod` 里；
- 使用者如果用了被撤回的版本，`go` 会给出警告；
- `@latest` 会避开被撤回的版本。

> `exclude` 是使用者排除别人，`retract` 是作者撤回自己，方向相反。

## 9.7 `go.sum`
`go.sum` 记录依赖内容的校验和（下面的哈希值省略）：

```
github.com/gin-gonic/gin v1.10.0 h1:...
github.com/gin-gonic/gin v1.10.0/go.mod h1:...
gorm.io/gorm v1.25.10 h1:...
gorm.io/gorm v1.25.10/go.mod h1:...
```

- 每个模块通常有两行：模块 zip 的哈希、`go.mod` 的哈希；
- 下载依赖时，Go 会校验内容是否匹配；
- 不匹配会报 `checksum mismatch`，可能是网络篡改或缓存损坏；
- **`go.sum` 不是 lock 文件**：它不决定版本，只校验内容；
- 版本由 `go.mod` 和 MVS 决定；
- `go.sum` 应该提交到版本库。

常用命令：

```powershell
go mod tidy       # 补全缺失的 go.sum 条目，删除无用条目
go mod download   # 下载依赖并校验
go mod verify     # 校验模块缓存是否被修改
```

`go mod verify` 输出：

```
all modules verified
```

如果缺少条目：

```
missing go.sum entry for module providing package github.com/gin-gonic/gin
```

执行 `go mod tidy` 或 `go mod download` 即可。

私有模块可以设置：

```powershell
go env -w GOPRIVATE=git.example.com/*
```

`GOPRIVATE` 会同时影响 `GONOPROXY` 和 `GONOSUMDB`：私有模块不走公共代理，也不校验公共校验和数据库。

## 9.8 语义化版本与 v2+ 路径
### 9.8.1 版本号格式
```
vMAJOR.MINOR.PATCH
v1.10.0
```

| 部分 | 含义 | 兼容性 |
|------|------|--------|
| MAJOR | 主版本 | 不兼容变更 |
| MINOR | 次版本 | 向后兼容的新功能 |
| PATCH | 补丁 | 向后兼容的修复 |

预发布版本：

```
v1.2.3-beta.1
v2.0.0-rc.1
```

构建元数据（如 `v1.2.3+build.5`）不参与版本比较。Go 模块版本通常不使用它，`+incompatible` 是特殊用途。

### 9.8.2 v0、v1、v2+
- `v0.x.y`：不稳定，随时可能破坏兼容；
- `v1.x.y`：稳定 API；
- `v2.x.y` 及以上：**模块路径必须带对应主版本后缀**（`/v2`、`/v3`……）。

例如：

```
module github.com/foo/bar/v2
```

导入：

```go
import "github.com/foo/bar/v2"
```

`v0` 和 `v1` 不需要后缀：

```
github.com/foo/bar       // v0.x 或 v1.x
github.com/foo/bar/v2    // v2.x
github.com/foo/bar/v3    // v3.x
```

不同主版本是**不同的模块**，可以同时存在于依赖图中。

### 9.8.3 伪版本（pseudo-version）
依赖某个尚未打 tag 的提交时，Go 会生成伪版本：

```
v0.0.0-20240115093000-abcdef123456
```

格式：

```
vX.Y.Z-yyyymmddhhmmss-abcdefabcdef
```

- 时间戳是 UTC；
- 后缀是提交哈希的前 12 位；
- 伪版本可以比较大小，但只是「某个提交」的临时标识；
- 正式发布时应打 tag，不要长期依赖伪版本。

### 9.8.4 `+incompatible`
一些早期模块在 v2+ 版本还没有 `go.mod`，Go 会用 `v2.0.0+incompatible` 表示这是不兼容主版本。新项目不要模仿这种布局。

## 9.9 依赖管理常用命令
### 9.9.1 `go get`
```powershell
go get github.com/gin-gonic/gin@v1.10.0
go get gorm.io/gorm@latest
go get github.com/gin-gonic/gin@none   # 移除依赖
go get -u ./...                        # 升级当前模块的依赖
go get -u=patch ./...                  # 只升级补丁版本
```

Go 1.17 起，`go get` 只修改依赖，不再安装可执行程序。安装工具用：

```powershell
go install golang.org/x/tools/cmd/stringer@latest
```

### 9.9.2 `go mod tidy`
```powershell
go mod tidy
```

- 添加代码中缺失的依赖；
- 删除不再使用的依赖；
- 补全 `go.sum`；
- 可能调整 `go` 指令和 `// indirect` 标记。

提交代码前通常都要跑一次。

### 9.9.3 `go mod download`
```powershell
go mod download
go mod download github.com/gin-gonic/gin
go mod download -json github.com/gin-gonic/gin
```

- 下载到 `GOMODCACHE`；
- 校验 `go.sum`；
- `-json` 输出 `Path`、`Version`、`Dir`、`Sum` 等字段。

### 9.9.4 `go list`
```powershell
go list -m all              # 当前构建列表中的所有模块
go list -m -u all           # 显示可升级的模块
go list -m -versions github.com/gin-gonic/gin
go list -m -json github.com/gin-gonic/gin
go list -m -f '{{.Dir}}' github.com/gin-gonic/gin
```

`go list -m all` 的第一行是主模块，没有版本号：

```
example.com/shop
github.com/gin-gonic/gin v1.10.0
gorm.io/gorm v1.25.10
...
```

### 9.9.5 其他诊断命令
```powershell
go mod why -m github.com/gin-gonic/gin   # 为什么需要这个模块
go mod graph                             # 打印模块依赖图
go mod verify                            # 校验模块缓存
go clean -modcache                       # 清空模块缓存（慎用，会重新下载）
```

## 9.10 `replace`：替换依赖
### 9.10.1 本地替换
```powershell
go mod edit -replace=example.com/legacy=../legacy
```

或在 `go.mod` 中手写：

```
replace example.com/legacy => ../legacy
```

`../legacy` 目录必须有 `go.mod`。

### 9.10.2 替换成另一个模块版本
```
replace github.com/foo/bar v1.2.3 => github.com/fork/bar v1.2.4
```

- 左边带版本：只替换这个版本；
- 左边不带版本：替换该模块的所有版本；
- 右边可以是模块路径 + 版本，也可以是本地目录；
- 本地目录路径必须以 `./`、`../` 或绝对路径开头。

### 9.10.3 重要限制
- `replace` 只在**主模块**的 `go.mod` 中生效；
- 依赖自己的 `go.mod` 里的 `replace` 会被忽略；
- 不会改变代码里的导入路径，代码仍然 `import "example.com/legacy"`；
- 发布库时不要依赖 `replace` 指向本地目录，否则别人构建不了。

常见用途：

- 调试第三方库，拉一份源码到本地改；
- 临时使用尚未合并的修复；
- 多模块项目本地联调。

调试完成后记得删除 `replace`，或把修改合并回正式依赖。

## 9.11 `vendor`：把依赖放进仓库
```powershell
go mod vendor
```

生成：

```
vendor/
├── modules.txt
└── github.com/...
```

- 把构建所需的依赖源码复制到 `vendor/`；
- `vendor/modules.txt` 记录模块版本和包列表；
- 当 `vendor/modules.txt` 存在且与 `go.mod` 一致时，Go 1.14+ 会自动使用 vendor 构建；
- 强制使用：`go build -mod=vendor`；
- 忽略 vendor：`go build -mod=mod`。

优点：

- 离线构建；
- 构建内容完全可复现；
- 不受代理或上游删库影响。

缺点：

- 仓库变大；
- 升级依赖要重新 `go mod vendor`；
- 安全补丁需要手动同步；
- 代码审查时 diff 很大。

使用 vendor 时，`go.mod` 和 `go.sum` 仍要提交。依赖变化后忘记重新 vendor，会报：

```
inconsistent vendoring
```

解决：重新执行 `go mod vendor`。

## 9.12 `go work`：多模块工作区
一个仓库里有两个模块：

```
workspace/
├── app/
│   ├── go.mod
│   └── main.go
└── lib/
    ├── go.mod
    └── lib.go
```

在根目录：

```powershell
go work init ./app ./lib
```

生成 `go.work`：

```
go 1.22

use (
    ./app
    ./lib
)
```

现在 `app` 可以直接导入 `lib` 的模块路径，无需 `replace`，也无需发布。

常用命令：

```powershell
go work use ./newmodule   # 加入新模块
go work sync              # 把工作区构建列表同步到各模块的 go.mod
go work vendor            # 为工作区生成 vendor
go env GOWORK             # 查看当前使用的 go.work
```

`go.work` 也可以写 `replace`，优先级高于各模块 `go.mod` 中的 `replace`。

注意：

- 工作区模式不改变模块路径，各模块仍然独立发布；
- `go.work` 通常不提交到库（它是开发者本地配置），团队统一 monorepo 时可以提交；
- 临时禁用：`$env:GOWORK="off"`（PowerShell）或 `GOWORK=off go build ./...`。

## 9.13 `GOPROXY` 与模块缓存
### 9.13.1 `GOPROXY`
```powershell
go env GOPROXY
# 默认类似：https://proxy.golang.org,direct
```

国内常用：

```powershell
go env -w GOPROXY=https://goproxy.cn,direct
# 也可用 https://goproxy.io,direct 或 https://mirrors.aliyun.com/goproxy/,direct
```

分隔符语义：逗号 `,` 遇到 404/410 才尝试下一个；竖线 `|` 遇到任何错误都尝试下一个；`direct` 直接从版本库下载；`off` 禁止网络下载。恢复默认用 `go env -u GOPROXY`。

### 9.13.2 校验和数据库
`go env GOSUMDB` 默认是 `sum.golang.org`。它校验模块内容，防止篡改；私有模块用 `GOPRIVATE` 跳过代理和校验和数据库，也可以单独设置 `GONOPROXY`、`GONOSUMDB`。不建议直接 `GOSUMDB=off`，除非你清楚风险。

### 9.13.3 模块缓存 `GOMODCACHE`
```powershell
go env GOMODCACHE
# 典型值：C:\Users\<用户名>\go\pkg\mod
```

缓存目录按模块路径和版本组织：

```
pkg/mod/
├── cache/download/
├── github.com/gin-gonic/gin@v1.10.0/
└── gorm.io/gorm@v1.25.10/
```

- 缓存是只读的，不要直接改；
- 需要改第三方代码时，用 `replace` 指向本地副本；
- `go clean -modcache` 会清空全部缓存，之后需要重新下载。

### 9.13.4 `GOTOOLCHAIN`
Go 1.21 起：

```powershell
go env GOTOOLCHAIN
# auto
```

如果 `go.mod` 要求的 Go 版本高于本地，`auto` 可能自动下载新工具链。离线环境可以设为 `local`，强制使用本地版本。

## 9.14 阅读第三方库：pkg.go.dev、`go doc` 与源码
### 9.14.1 pkg.go.dev
打开 <https://pkg.go.dev/github.com/gin-gonic/gin>，重点看：

| 区域 | 用途 |
|------|------|
| Doc | 包说明、示例、导出 API |
| Index | 常量、变量、函数、类型及其方法 |
| Versions | 所有版本，可切换 |
| Licenses | 许可证 |
| Imports | 该模块依赖了谁 |
| Imported by | 谁在使用它 |
| Source | 跳到源码 |

读文档的顺序：

1. 包级说明（这个包解决什么问题）；
2. 核心类型和构造函数；
3. 常用方法；
4. 示例代码；
5. 需要细节时再点 Source。

### 9.14.2 `go doc`
```powershell
go doc fmt.Println
go doc github.com/gin-gonic/gin
go doc github.com/gin-gonic/gin.Engine
go doc -all github.com/gin-gonic/gin   # 全部导出 API
go doc -src github.com/gin-gonic/gin.New  # 看源码
```

`go doc` 查的是本地模块缓存中的版本，和 `go.mod` 一致。

### 9.14.3 定位源码目录
```powershell
go list -m -f '{{.Dir}}' github.com/gin-gonic/gin
# <GOMODCACHE>\github.com\gin-gonic\gin@v1.10.0

go mod download -json github.com/gin-gonic/gin
# 输出中包含 "Dir": "..."
```

然后可以直接用编辑器打开该目录，或：

```powershell
go doc -src github.com/gin-gonic/gin.Engine.ServeHTTP
```

### 9.14.4 读源码的方法
1. 先看 `README.md`、`doc.go`、包注释；
2. 找到核心类型（Gin 的 `Engine`、`Context`，GORM 的 `DB`、`Statement`）；
3. 顺着导出方法看调用链；
4. 看 `_test.go`，测试往往是最好的用法示例；
5. 不要一上来读全部内部实现，先建立类型地图。

> 模块缓存里的代码是只读的；想改就用 `replace` 复制到本地。

## 9.15 依赖选择原则
引入第三方依赖前，至少检查：

| 维度 | 要看什么 |
|------|----------|
| 维护状态 | 最近提交、发版频率、issue 响应 |
| 版本 | 是否遵循 semver，是否已到 v1+ |
| 许可证 | MIT / Apache-2.0 / BSD 通常安全；GPL 需谨慎 |
| 安全 | 是否有已知漏洞，依赖是否过多 |
| API 设计 | 是否接受 `context`、是否易于测试、是否过度抽象 |
| 传递依赖 | 会不会带进大量不需要的模块 |
| 社区 | 文档、示例、使用者数量（star 只是参考） |
| 可替换性 | 锁定成本高不高，是否有成熟替代品 |

对 Gin/GORM 这类成熟框架，重点不是「要不要用」，而是：

- 版本是否与 Go 版本兼容；
- 驱动是否匹配数据库；
- 是否引入了不需要的插件；
- 升级时是否阅读 release notes。

## 9.16 与 Gin/GORM 的关联：模块路径与版本
### 9.16.1 Gin
模块路径是 `github.com/gin-gonic/gin`，安装 `go get github.com/gin-gonic/gin@v1.10.0`，导入：

```go
import "github.com/gin-gonic/gin"
```

Gin 目前是 v1.x，路径不带 `/v1`；如果将来发布 v2，路径会变成 `github.com/gin-gonic/gin/v2`。扩展通常是独立模块：`github.com/gin-contrib/cors`、`github.com/gin-contrib/sessions`、`github.com/gin-contrib/static`。

### 9.16.2 GORM
模块路径是 `gorm.io/gorm`。**容易混淆**：产品叫「GORM v2」，但 Go 模块仍以 v1.x 发布（例如 `v1.25.x`），路径没有 `/v2`，不要写成 `gorm.io/gorm/v2`。

```powershell
go get gorm.io/gorm@v1.25.10
go get gorm.io/driver/mysql@v1.5.6
```

```go
import (
    "gorm.io/driver/mysql"
    "gorm.io/gorm"
)
```

驱动是独立模块：`gorm.io/driver/mysql`、`gorm.io/driver/postgres`、`gorm.io/driver/sqlite`、`gorm.io/driver/sqlserver`、`gorm.io/driver/clickhouse`。其他独立模块还有 `gorm.io/hints`、`gorm.io/gen`、`gorm.io/datatypes`、`gorm.io/plugin/dbresolver`。

### 9.16.3 不要混用 GORM v1
GORM v1 的导入路径是 `github.com/jinzhu/gorm`，与 `gorm.io/gorm` 是两套 API，不能混用；看文档先确认版本。

## 9.17 常见错误与陷阱
| 错误/现象 | 原因 | 修复 |
|-----------|------|------|
| `no required module provides package ...` | 依赖未添加 | `go get 包路径` 或 `go mod tidy` |
| `missing go.sum entry` | 校验和缺失 | `go mod tidy` / `go mod download` |
| `module ... found, but does not contain package ...` | 路径写错或版本不对 | 检查子目录和版本 |
| `cannot find module providing package ...` | 代理/网络/路径错误 | 检查 `GOPROXY` 和拼写 |
| `import cycle not allowed` | 包之间循环导入 | 抽取公共包或调整依赖方向 |
| `use of internal package ... not allowed` | 越过 `internal` 边界 | 把调用方放进允许的目录树 |
| `found packages a and b in ...` | 一个目录两个包名 | 拆分目录或统一包名 |
| `is a program, not an importable package` | 导入了 `package main` | 改为导入库包 |
| `imported and not used` | 导入未使用 | 使用、删除或改空白导入 |
| `inconsistent vendoring` | vendor 与 go.mod 不一致 | 重新 `go mod vendor` |
| `replacement module without version must be directory path` | replace 右边缺版本且不是目录 | 加版本或改成 `./` / `../` 路径 |
| `replacement directory ... does not exist` | 本地路径错误 | 检查相对路径 |
| `module declares its path as ... but was required as ...` | 模块路径不一致 | 修正 `module` 声明或 replace |
| `go.mod file indicates go 1.22, but maximum supported version is 1.21` | 工具链太旧 | 升级 Go 或调低 `go` 指令 |
| `updates to go.mod needed; to update it: go mod tidy` | go.mod 过期 | 执行 `go mod tidy` |
| `ambiguous import` | 两个模块提供同一包 | 用 `replace`/`exclude` 或换依赖 |
| `dial tcp ... i/o timeout` | 代理不可达 | 换 `GOPROXY` 或检查网络 |
| `checksum mismatch` | 缓存损坏或被篡改 | `go clean -modcache` 后重下 |

补充：

- `go.mod` 里的版本是「最低要求」，不是「锁定版本」；
- `go.sum` 只校验内容，不决定版本；
- `replace` 只对主模块生效，发布库时不要留本地路径；
- 使用 vendor 后，修改依赖要重新 `go mod vendor`；
- `go.work` 是本地开发配置，通常不提交；
- `git.example.com` 这类私有域名要配置 `GOPRIVATE`。

## 9.20 本章小结
| 概念 | 一句话解释 | 易错点 |
|------|------------|--------|
| 包 | 一个目录下的 `.go` 文件集合 | 一个目录只能有一个包名 |
| 导入路径 | 模块路径 + 子目录 | 不是文件系统路径 |
| `package main` | 可执行程序入口 | 不能被导入 |
| 别名导入 | 给包起别名 | 只影响当前文件 |
| 空白导入 | 只执行 `init` | 用于注册驱动 |
| 点导入 | 省略包名前缀 | 不推荐 |
| 导出 | 首字母大写 | 小写字段 JSON/GORM 看不到 |
| `init` | 包初始化时自动执行 | 不要做重活、不要依赖顺序 |
| `internal` | 限制导入范围 | 规则基于导入路径 |
| `go.mod` | 模块声明与依赖要求 | 版本是最低要求 |
| `go.sum` | 依赖内容校验和 | 不是 lock 文件 |
| MVS | 最小版本选择 | 选中的是所有要求中的最大值 |
| semver | 主/次/补丁 | v2+ 路径带主版本后缀 |
| 伪版本 | 未打 tag 的提交 | 不要长期依赖 |
| `go get` | 添加/升级依赖 | 不再安装可执行程序 |
| `go mod tidy` | 整理依赖 | 提交前跑一次 |
| `go list -m all` | 查看构建列表 | 第一行是主模块 |
| `replace` | 替换依赖 | 只对主模块生效 |
| `vendor` | 依赖放进仓库 | 记得重新生成 |
| `go work` | 多模块工作区 | 通常不提交 |
| `GOPROXY` | 模块代理 | 国内常用 goproxy.cn |
| `GOMODCACHE` | 模块缓存 | 不要直接修改 |
