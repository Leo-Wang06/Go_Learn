## 8.1 `error` 到底是什么
`error` 是一个只有一个方法的普通接口：

```go
type error interface {
    Error() string
}
```

任何类型只要实现 `Error() string`，就是错误：

```go
package main

import "fmt"

type MyError struct{ Msg string }

func (e MyError) Error() string { return e.Msg }

func main() {
    var err error = MyError{Msg: "something went wrong"}
    fmt.Println(err)        // something went wrong
    fmt.Printf("%T\n", err) // main.MyError
}
```

输出：

```
something went wrong
main.MyError
```

### 8.1.1 与 TypeScript try/catch 对照
| 维度 | TypeScript | Go |
|------|------------|-----|
| 错误传递 | `throw` 自动向上抛 | `return err` 显式向上传 |
| 捕获 | `try/catch` | `if err != nil` |
| 错误类型 | 任意 `throw` 值 | 必须实现 `Error() string` |

TypeScript 的 `throw` 会打断正常流程；Go 的错误是函数的普通返回值。好处是每个失败点都看得见，代价是 `if err != nil` 会写很多次。

> **心智模型**：Go 把错误当作「函数的普通输出之一」，不是异常。

## 8.2 创建错误：`errors.New` 与 `fmt.Errorf`
```go
err := errors.New("user not found")         // 固定错误
err = fmt.Errorf("user %d not found", id)   // 带上下文
```

```go
package main

import (
    "errors"
    "fmt"
)

var ErrUserNotFound = errors.New("user not found")

func findUserName(id int) (string, error) {
    if id != 1 {
        return "", ErrUserNotFound
    }
    return "张三", nil
}

func main() {
    name, err := findUserName(2)
    if err != nil {
        if errors.Is(err, ErrUserNotFound) {
            fmt.Println("用户不存在：", err)
            return
        }
        fmt.Println("其他错误：", err)
        return
    }
    fmt.Println(name)
}
```

输出：

```
用户不存在： user not found
```

`fmt.Errorf` 带动态参数时不要用 `==` 比较：

```go
base := errors.New("not found")
wrapped := fmt.Errorf("find user: %w", base)

fmt.Println(wrapped == base)          // false
fmt.Println(errors.Is(wrapped, base)) // true
```

## 8.3 错误返回惯例
### 8.3.1 `error` 放最后一个返回值
常见签名：`func LoadUser(id int64) (*User, error)`、`func ParseInt(s string) (int, error)`、`func Open(path string) (*os.File, error)`。

### 8.3.2 立即检查，尽早返回
```go
user, err := LoadUser(1)
if err != nil {
    return fmt.Errorf("load user: %w", err)
}
order, err := LoadOrder(user.ID)
if err != nil {
    return fmt.Errorf("load order for user %d: %w", user.ID, err)
}
// 主逻辑保持平铺
```

不要写「成功才进入一大段嵌套」的代码。

### 8.3.3 不要忽略错误
```go
data, _ := json.Marshal(v) // 只在你确定失败无所谓时才这样写
```

`json.Marshal` 对 channel、func、循环引用等会失败。业务代码应处理：

```go
data, err := json.Marshal(v)
if err != nil {
    return fmt.Errorf("marshal response: %w", err)
}
```

### 8.3.4 错误与返回值
返回错误时，其他返回值通常应是零值：

```go
func LoadUser(id int64) (*User, error) {
    u, err := query(id)
    if err != nil {
        return nil, err // 不要返回半成品
    }
    return u, nil
}
```

### 8.3.5 底层只包装，上层只记录
```go
// repository：包装并返回，不记录
return fmt.Errorf("find user %d: %w", id, err)
// handler：记录一次，并映射响应
h.logger.Error("get user failed", "user_id", id, "err", err)
writeError(c, err)
```

如果每一层都 `log.Println(err)`，同一个错误会被记录多次，日志噪音大，还容易泄露内部信息。

## 8.4 哨兵错误（Sentinel Error）
预定义好的、表示特定含义的错误值：

```go
var (
    ErrUserNotFound     = errors.New("user not found")
    ErrInvalidArgument  = errors.New("invalid argument")
    ErrPermissionDenied = errors.New("permission denied")
)
```

规范：导出名 `ErrXxx`，用 `var` 而不是 `const`，当作只读值，注释说明何时返回。

### 8.4.1 `io.EOF`
表示输入流结束，不是故障：

```go
package main
import (
    "fmt"
    "io"
    "strings"
)

func main() {
    r := strings.NewReader("")
    buf := make([]byte, 10)
    n, err := r.Read(buf)
    fmt.Println(n, err)        // 0 EOF
    fmt.Println(err == io.EOF) // true
}
```

输出：

```
0 EOF
true
```

读文件、网络流时，`io.EOF` 是正常结束信号，通常不应作为错误上报。

### 8.4.2 `sql.ErrNoRows`
`QueryRow.Scan` 没有查到行时返回它：

```go
var name string
err := db.QueryRowContext(ctx, "SELECT name FROM users WHERE id = ?", id).Scan(&name)
if errors.Is(err, sql.ErrNoRows) {
    return nil, ErrUserNotFound
}
```

其他错误同样要包装后返回。`Query` 返回空结果集时不会返回 `sql.ErrNoRows`，只有 `QueryRow.Scan` 会。

### 8.4.3 `gorm.ErrRecordNotFound`
```go
var u User
err := db.WithContext(ctx).First(&u, "id = ?", id).Error
if errors.Is(err, gorm.ErrRecordNotFound) {
    return nil, ErrUserNotFound
}
```

其他错误同样要包装后返回。GORM v2 中：

- `First`、`Take`、`Last` 查不到记录时返回 `gorm.ErrRecordNotFound`；
- `Find` 查不到时返回**空切片 + nil 错误**；
- `Count`、`Pluck` 也不返回该错误；
- 不要使用 v1 的 `db.RecordNotFound`，v2 已移除。

哨兵错误只能表达「是什么」，不能携带字段、错误码等信息；需要更多信息时用自定义错误类型（8.8 节）。

## 8.5 错误包装：`%w`
底层错误往往缺少上下文。包装后：

```
load config "config.yaml": open config.yaml: The system cannot find the file specified.
```

### 8.5.1 `%w` 与 `%v`
```go
if err != nil {
    return fmt.Errorf("load config %q: %w", path, err)
}
```

| 动词 | 输出 | 保留错误链 |
|------|------|------------|
| `%v` / `%s` | 原错误文本 | 否 |
| `%w` | 原错误文本 | **是** |
| `%q` | 带引号的文本 | 否 |

### 8.5.2 完整示例
```go
package main
import (
    "errors"
    "fmt"
)

var ErrNotFound = errors.New("not found")

func repoFind(id int) error {
    return fmt.Errorf("repo: user %d: %w", id, ErrNotFound)
}

func serviceFind(id int) error {
    if err := repoFind(id); err != nil {
        return fmt.Errorf("service: %w", err)
    }
    return nil
}

func main() {
    err := serviceFind(7)
    fmt.Println(err)                         // service: repo: user 7: not found
    fmt.Println(errors.Is(err, ErrNotFound)) // true
    fmt.Println(err == ErrNotFound)          // false
    fmt.Println(errors.Unwrap(err) == nil)   // false
}
```

输出：

```
service: repo: user 7: not found
true
false
false
```

错误链是 `service: ...` → `repo: ...` → `not found`。

### 8.5.3 `Unwrap`
`errors.Unwrap` 只解一层；判断整条链用 `errors.Is`。实现了 `Unwrap() error` 或 `Unwrap() []error` 的错误可以被解链。

```go
wrapped := fmt.Errorf("context: %w", ErrNotFound)
fmt.Println(errors.Unwrap(wrapped) == ErrNotFound) // true
```

### 8.5.4 不要包装 nil
```go
var err error
wrapped := fmt.Errorf("context: %w", err)
fmt.Println(wrapped == nil) // false
fmt.Println(wrapped)        // context: %!w(<nil>)
```

先判断 `err != nil`，再包装。

## 8.6 `errors.Is`：判断错误链中是否包含目标
```go
if errors.Is(err, ErrNotFound) {
    // err 本身是 ErrNotFound，或链上某一层是
}
```

判断顺序（简化）：先 `err == target`；若 `err` 实现了 `Is(error) bool` 就调用；否则解包一层继续。

```go
fmt.Println(err == ErrNotFound)          // false：被包装过
fmt.Println(errors.Is(err, ErrNotFound)) // true：穿透包装
```

**只要错误可能被包装过，就用 `errors.Is`，不要用 `==`。**

### 8.6.1 自定义 `Is` 方法
两个错误「码相同」就算同类时：

```go
package main
import (
    "errors"
    "fmt"
)

type QueryError struct {
    Code int
    Msg  string
}

func (e *QueryError) Error() string {
    return fmt.Sprintf("query error %d: %s", e.Code, e.Msg)
}

// 按 Code 判断，而不是按指针相等。
func (e *QueryError) Is(target error) bool {
    t, ok := target.(*QueryError)
    return ok && t.Code == e.Code
}

func main() {
    err := fmt.Errorf("load: %w", &QueryError{Code: 404, Msg: "no rows"})
    fmt.Println(err) // load: query error 404: no rows
    fmt.Println(errors.Is(err, &QueryError{Code: 404})) // true
    fmt.Println(errors.Is(err, &QueryError{Code: 500})) // false
}
```

输出：

```
load: query error 404: no rows
true
false
```

自定义 `Is` 会被整条链上的 `errors.Is` 调用，只在你确实需要「按语义比较」时使用。

## 8.7 `errors.As`：取出错误链中的某类错误
`errors.Is` 只能回答「是不是」，`errors.As` 还能拿到错误里的字段。

```go
package main
import (
    "errors"
    "fmt"
)

type ValidationError struct {
    Field string
    Msg   string
}

func (e *ValidationError) Error() string {
    return fmt.Sprintf("validation failed: %s: %s", e.Field, e.Msg)
}

func validateAge(age int) error {
    if age < 0 {
        return fmt.Errorf("validate age: %w", &ValidationError{
            Field: "age", Msg: "must be non-negative",
        })
    }
    return nil
}

func main() {
    err := validateAge(-1)
    fmt.Println(err)

    var ve *ValidationError
    if errors.As(err, &ve) {
        fmt.Println("field:", ve.Field)
    }
}
```

输出：

```
validate age: validation failed: age: must be non-negative
field: age
```

### 8.7.1 目标变量规则
目标必须是非 nil 指针，且指向的类型要实现 `error`（或指向接口类型）。

```go
var ve *ValidationError
ok := errors.As(err, &ve) // 正确
```

如果错误类型的方法用**值接收者**，目标应为 `var ve ValidationError; errors.As(err, &ve)`。错误写法 `var s string; errors.As(err, &s)` 会 panic，因为 `string` 没有实现 `error`。

### 8.7.2 `Is` 与 `As` 的选择
| 需求 | 用哪个 |
|------|--------|
| 判断是不是某个哨兵错误 | `errors.Is` |
| 判断是不是某一类错误（按码） | `errors.Is` + 自定义 `Is` |
| 读取错误里的字段 | `errors.As` |
| 拿到原始错误类型 | `errors.As` |
| 比较错误文本 | 都不要 |

**`Is` 问「是不是」，`As` 拿「是什么」。**

## 8.8 自定义错误类型
### 8.8.1 携带业务错误码
```go
package main
import (
    "errors"
    "fmt"
)

type AppError struct {
    Code    int    // 业务错误码
    Message string // 可展示给用户的信息
    Err     error  // 内部原始错误，可为 nil
}

func (e *AppError) Error() string {
    if e.Err == nil {
        return fmt.Sprintf("%s (code=%d)", e.Message, e.Code)
    }
    return fmt.Sprintf("%s (code=%d): %v", e.Message, e.Code, e.Err)
}

// Unwrap 让 errors.Is / errors.As 能继续向内查找。
func (e *AppError) Unwrap() error { return e.Err }

func main() {
    base := errors.New("connection refused")
    err := &AppError{Code: 5001, Message: "database unavailable", Err: base}
    fmt.Println(err)
    fmt.Println(errors.Is(err, base)) // true
    var appErr *AppError
    if errors.As(err, &appErr) {
        fmt.Println("biz code:", appErr.Code)
    }
}
```

输出：

```
database unavailable (code=5001): connection refused
true
biz code: 5001
```

### 8.8.2 在 service 层翻译错误
```go
if errors.Is(err, gorm.ErrRecordNotFound) {
    return nil, &AppError{Code: 4041, Message: "user not found", Err: err}
}
return nil, fmt.Errorf("get user %d: %w", id, err)
```

一旦用 `Err` 字段或 `%w` 保留原始错误，上层仍可以用 `errors.Is` 找到 `gorm.ErrRecordNotFound`。

### 8.8.3 接收者用值还是指针
| 接收者 | 场景 | `errors.As` 目标 |
|--------|------|------------------|
| `*T` | 需要修改、对象较大、常规选择 | `var e *T`，传 `&e` |
| `T` | 小型不可变值 | `var e T`，传 `&e` |

同一项目保持一致。不要用错误类型模拟「成功、失败、部分成功」等业务状态。

## 8.9 错误信息设计
英文错误信息规范：小写开头、不加句号、不加 `error:` 前缀、带上下文。中文同样要求简洁、带上下文、不加句号、不泄露敏感信息。

好例子：

```go
return fmt.Errorf("create order for user %d: %w", userID, err)
return fmt.Errorf("decode request body: %w", err)
return fmt.Errorf("open config %q: %w", path, err)
```

它们回答：在做什么、对谁做、为什么失败。

| 写法 | 问题 |
|------|------|
| `errors.New("failed")` | 没有上下文 |
| `errors.New("Error occurred.")` | 大写 + 句号 + 无信息 |
| `fmt.Errorf("error: %v", err)` | 重复前缀 |
| `fmt.Errorf("user %s password %s invalid", email, password)` | 泄露敏感信息 |
| `fmt.Errorf(err.Error())` | 丢失包装，格式字符串有注入风险 |

### 8.9.1 错误信息不是用户提示
`error.Error()` 是给开发者看的。用户看到的是：

```json
{"code": "USER_NOT_FOUND", "message": "用户不存在"}
```

不要把 SQL、文件路径、堆栈、内网 IP 返回给客户端。也不要在测试或上层逻辑里比较错误文本，用哨兵错误、错误码或自定义类型来稳定判断。

## 8.10 错误与日志的边界
| 层 | 职责 | 是否记录日志 |
|----|------|--------------|
| repository / dao | 执行操作，包装上下文 | 否 |
| service | 业务规则、错误翻译、包装 | 通常否 |
| handler / consumer | 记录一次、映射响应 | 是 |
| middleware | 兜底 panic、请求日志、统一响应 | 是 |

```go
// repository
return fmt.Errorf("find user %d: %w", id, err)

// service
if errors.Is(err, gorm.ErrRecordNotFound) {
    return nil, ErrUserNotFound
}
return nil, fmt.Errorf("get user %d: %w", id, err)

// handler：只在能处理错误的层记录
u, err := h.svc.Get(ctx, id)
if err != nil {
    h.logger.Error("get user failed",
        "request_id", requestID, "user_id", id, "err", err)
    writeError(c, err)
    return
}
```

### 8.10.1 日志级别
| 情况 | 建议级别 |
|------|----------|
| 可预期业务错误（参数校验失败、未找到） | Info / Warn |
| 依赖失败但可重试（超时、连接断开） | Warn |
| 未预期系统错误（空指针、数据不一致） | Error |

结构化日志（第 12 章详讲）：

```go
slog.Error("create order failed",
    "request_id", requestID, "user_id", userID, "err", err)
```

日志不等于监控；关键错误还需要指标和告警（第 15 章）。

## 8.11 `errors.Join`：合并多个错误
Go 1.20 新增，适合「多个操作都失败，但都想报告」的场景。

```go
package main

import (
    "errors"
    "fmt"
)

func main() {
    err1 := errors.New("db timeout")
    err2 := errors.New("cache miss")
    joined := errors.Join(err1, err2)

    fmt.Println(joined)
    fmt.Println(errors.Is(joined, err1))       // true
    fmt.Println(errors.Is(joined, err2))       // true
    fmt.Println(errors.Join(nil, nil) == nil)  // true
}
```

输出：

```
db timeout
cache miss
true
true
true
```

要点：

- 忽略 nil 参数；全为 nil 时返回 nil；
- 返回的错误实现 `Unwrap() []error`；
- `errors.Is` / `errors.As` 会遍历所有子错误；
- `errors.Unwrap` 对多错误返回 nil（签名只支持单错误）；
- `Error()` 用换行连接子错误。

### 8.11.1 批量关闭资源
```go
func closeAll(closers ...io.Closer) error {
    var errs []error
    for _, c := range closers {
        if err := c.Close(); err != nil {
            errs = append(errs, err)
        }
    }
    return errors.Join(errs...)
}
```

### 8.11.2 批量校验
```go
func validate(req CreateUserReq) error {
    var errs []error
    if req.Name == "" {
        errs = append(errs, errors.New("name is required"))
    }
    if req.Age < 0 {
        errs = append(errs, errors.New("age must be non-negative"))
    }
    return errors.Join(errs...)
}
```

`errors.Join` 的错误文本是多行，直接返回给用户时通常需要转换成一组成员列表。

## 8.12 `panic` 与 `recover` 的边界
### 8.12.1 什么时候返回 error
绝大多数「可预期」的失败都应返回 error：参数不合法、查询不到、网络超时、约束冲突、文件不存在、权限不足。

### 8.12.2 什么时候可以 panic
只用于程序自身不可恢复的错误：初始化阶段缺少必需配置、不可能发生的分支（穷举枚举后出现未知值）、编程错误（nil map 写入、数组越界等，由运行时 panic）。

库代码尤其不应随意 panic，调用方无法预期，也无法用 `if err != nil` 处理。

### 8.12.3 `recover` 的用法
```go
package main
import "fmt"

func safeDivide(a, b int) (result int, err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("divide %d by %d: %v", a, b, r)
        }
    }()
    return a / b, nil
}

func main() {
    fmt.Println(safeDivide(10, 2))
    fmt.Println(safeDivide(1, 0))
}
```

输出：

```
5 <nil>
0 divide 1 by 0: runtime error: integer divide by zero
```

要点：

- `recover` 必须在 `defer` 的函数中**直接调用**；
- panic 后函数不继续执行，但 `defer` 会执行；
- 命名返回值可以在 `defer` 中修改；
- 恢复后函数正常返回。

### 8.12.4 `recover` 不能跨 goroutine
子 goroutine 的 panic 不会被主 goroutine 的 `recover` 捕获，整个程序会崩溃。每个 goroutine 如果需要兜底，必须自己 `defer recover`。

### 8.12.5 只在边界转换
只在最外层做一次 panic → error/500 的转换，例如 HTTP 中间件（`gin.Recovery()`）、后台任务 worker、RPC 服务端。不要在每一层都 `recover`，否则会掩盖真正的 bug。

恢复时用 `runtime.Stack(buf, false)` 记录堆栈，再通过 `slog.Error("panic recovered", "panic", r, "stack", ...)` 输出；只打印 `r` 往往不够。

`gin.Default()` 自带 Logger 和 Recovery；生产环境建议自定义 Recovery，接入结构化日志和统一错误响应。

## 8.13 与 GORM 的关联：错误处理
### 8.13.1 每个操作都返回 `*gorm.DB`
错误放在 `Error` 字段：

```go
result := db.Create(&user)
if result.Error != nil {
    return fmt.Errorf("create user: %w", result.Error)
}
```

`db.Create(&user)` 的返回值必须检查，不能直接丢弃。

### 8.13.2 `First` 与 `Find` 的差异
```go
var user User
err := db.First(&user, "id = ?", id).Error
if errors.Is(err, gorm.ErrRecordNotFound) {
    return nil, ErrUserNotFound
}
if err != nil {
    return nil, fmt.Errorf("find user %d: %w", id, err)
}
```

```go
var users []User
err := db.Where("age > ?", 18).Find(&users).Error
if err != nil {
    return nil, fmt.Errorf("list users: %w", err)
}
// 没有记录时 users 是空切片，err 是 nil
```

| 方法 | 查不到时 |
|------|----------|
| `First` / `Take` / `Last` | `gorm.ErrRecordNotFound` |
| `Find` | 空结果 + `nil` |
| `Count` | 0 + `nil` |
| `Pluck` | 空切片 + `nil` |

### 8.13.3 `RowsAffected`
适合更新和删除：

```go
result := db.Model(&User{}).Where("id = ?", id).Update("name", name)
if result.Error != nil {
    return fmt.Errorf("update user %d: %w", id, result.Error)
}
if result.RowsAffected == 0 {
    return ErrUserNotFound
}
```

- 新值和旧值相同时，某些数据库返回的 `RowsAffected` 可能是 0；
- 不要用 `RowsAffected` 判断查询是否为空，查询用 `len(users)` 或 `ErrRecordNotFound`；
- 软删除的删除操作实际是 `UPDATE deleted_at`，同样要看影响行数。

### 8.13.4 零值更新不会报错
```go
db.Model(&user).Updates(User{Name: "张三", Age: 0})
```

`Age: 0` 是零值，GORM 默认忽略，SQL 不会更新 `age`。解决方式：

```go
db.Model(&user).Updates(map[string]any{"name": "张三", "age": 0})
// 或者
db.Model(&user).Select("name", "age").Updates(User{Name: "张三", Age: 0})
```

### 8.13.5 事务中的错误
```go
err := db.Transaction(func(tx *gorm.DB) error {
    if err := tx.Create(&order).Error; err != nil {
        return fmt.Errorf("create order: %w", err)
    }
    if err := tx.Model(&Account{}).
        Where("id = ?", accountID).
        Update("balance", gorm.Expr("balance - ?", amount)).Error; err != nil {
        return fmt.Errorf("deduct balance: %w", err)
    }
    return nil
})
```

- 返回 `nil`：提交；返回任何 `error`：回滚；
- `panic`：GORM 回滚后重新抛出，需要外层 recover；
- 事务内部不要吞掉错误，否则可能误提交。

`ErrRecordNotFound` 在事务里同样会出现。如果「查不到」是正常分支，显式返回 `nil` 继续，不要让整个事务回滚：`if errors.Is(err, gorm.ErrRecordNotFound) { return nil }`。是否回滚取决于业务语义，不取决于错误类型。

## 8.14 HTTP 错误映射（预告）
原则：业务错误 → 4xx，系统错误 → 5xx；不返回内部错误文本；响应带稳定业务码；日志带 request ID；同一类错误在一处映射。

| 错误 | HTTP | 业务码示例 |
|------|------|------------|
| 参数校验失败 / `ValidationError` | 400 | `INVALID_ARGUMENT` |
| 未登录 / token 无效 | 401 | `UNAUTHORIZED` |
| 权限不足 | 403 | `FORBIDDEN` |
| `ErrUserNotFound` / `gorm.ErrRecordNotFound` | 404 | `NOT_FOUND` |
| 唯一键冲突 | 409 | `CONFLICT` |
| `context.DeadlineExceeded` | 504 | `TIMEOUT` |
| 其他内部错误 | 500 | `INTERNAL` |

Gin 中的统一错误响应：

```go
func writeError(c *gin.Context, err error) {
    var ve *ValidationError

    switch {
    case errors.As(err, &ve):
        c.JSON(http.StatusBadRequest, gin.H{
            "code": "INVALID_ARGUMENT", "message": ve.Error(),
        })
    case errors.Is(err, ErrUserNotFound), errors.Is(err, gorm.ErrRecordNotFound):
        c.JSON(http.StatusNotFound, gin.H{
            "code": "NOT_FOUND", "message": "用户不存在",
        })
    case errors.Is(err, context.DeadlineExceeded):
        c.JSON(http.StatusGatewayTimeout, gin.H{
            "code": "TIMEOUT", "message": "请求超时",
        })
    default:
        c.JSON(http.StatusInternalServerError, gin.H{
            "code": "INTERNAL", "message": "服务器内部错误",
        })
    }
}
```

handler 中记录日志后调用：

```go
u, err := h.svc.Get(c.Request.Context(), id)
if err != nil {
    h.logger.Error("get user failed",
        "request_id", c.GetString("request_id"), "user_id", id, "err", err)
    writeError(c, err)
    return
}
```

不要把 `err.Error()` 直接返回给客户端：

```go
c.JSON(500, gin.H{"error": err.Error()}) // 可能泄露 SQL、表名、路径、内网地址
```

详细信息只写日志。参数解析错误目前会落到 500，更完整的做法是定义 `ErrInvalidArgument` 或 `ValidationError`，让参数错误稳定映射到 400；第 16 章会在实战中完善。

## 8.15 常见错误与陷阱
| 错误/现象 | 原因 | 修复 |
|-----------|------|------|
| `errors.Is` 为 false | 包装用了 `%v` | 改用 `%w` |
| `errors.As` panic | 目标不是指向错误类型的非 nil 指针 | `var e *T; errors.As(err, &e)` |
| 包装后非 nil 但原错误是 nil | `%w` 包装 nil | 先判断 `err != nil` |
| 日志重复 | 每层都 log | 只在边界记录一次 |
| `recover()` 返回 nil | 不在 defer 中直接调用 | 放进 `defer func(){...}()` |
| 子 goroutine panic 导致进程退出 | recover 不能跨 goroutine | 每个 goroutine 自己 recover |
| 查不到记录返回 500 | 没判断 `ErrRecordNotFound` | 映射为 404 |
| `Find` 后用 `ErrRecordNotFound` 判断 | `Find` 不返回该错误 | 判断 `len(users)` |
| 更新 0 行却认为成功 | 没看 `RowsAffected` | 检查影响行数 |
| 更新零值失败 | GORM 忽略结构体零值 | 用 map 或 Select |
| `errors.Unwrap` 对 Join 返回 nil | 多错误用 `Unwrap() []error` | 用 `errors.Is`/`As` |

补充：

- `errors.Is(nil, nil)` 为 true，`errors.Is(err, nil)` 等价于 `err == nil`；包装默认用 `%w`，确实不需要上层判断原始错误时才用 `%v`；
- `panic` 不是 `throw`，可预期的业务分支一律返回 error；错误文本里不能出现密码、token、身份证号、银行卡号；
- `defer` 中 `recover` 后必须显式设置返回值，否则调用方会收到 nil 错误。

## 8.18 本章小结
| 概念 | 一句话解释 | 易错点 |
|------|------------|--------|
| `error` | `Error() string` 接口 | 不是异常 |
| 哨兵错误 | 预定义的错误值 | 包装后用 `errors.Is` |
| `io.EOF` | 流结束 | 通常不是故障 |
| `sql.ErrNoRows` | `QueryRow` 无结果 | `Query` 不返回它 |
| `gorm.ErrRecordNotFound` | `First/Take/Last` 无结果 | `Find` 不返回它 |
| `%w` | 包装并保留错误链 | 不要包装 nil |
| `errors.Is` | 判断链上是否有目标 | 不要用 `==` |
| `errors.As` | 提取链上的错误类型 | 目标必须是非 nil 指针 |
| 错误信息 | 操作 + 对象 + 原因 | 小写、无句号、不泄露敏感信息 |
| `errors.Join` | 合并多个错误 | 全 nil 时返回 nil |
| `panic` | 程序级不可恢复错误 | 不要用于业务分支 |
| `recover` | defer 中捕获 panic | 不能跨 goroutine |
| GORM 错误 | 看 `result.Error` | 不要忽略返回值 |
| `RowsAffected` | 影响行数 | 更新 0 行不一定是错误 |
| HTTP 映射 | 业务 4xx，系统 5xx | 不返回内部错误文本 |
